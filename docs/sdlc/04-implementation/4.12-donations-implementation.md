## 1. Scope

Deliver the approved financial-transparency surface: **campaign lifecycle**
(create → submit → verify → active, BR-007 public visibility), an **idempotent,
throttled donate flow** (FR-CAM-004/005, BR-008), **provider-agnostic payments**
with a **webhook-verified confirmation path**, donor-visible **history + receipts**
(DON-007/008), **oversight + refunds** (FR-CAM-006, FR-PAY-004) and the
**financial donation mobile UX** (§22, DON-001..008). All provider interaction runs
against the bundled **sandbox** only; nothing is claimed as a live-provider
integration (see §7).

### 2.1 Endpoint surface (approved matrix §13)

- `GET /api/campaigns/` — ACTIVE/CLOSED verified campaigns (`?q=` search), paginated.
- `GET /api/campaigns/{uid}/` — public detail; owner sees draft/owner rows; else 404.
- `POST /api/campaigns/` — `campaigns.create` (SUP/ADM + PATIENT/ORGANIZATION — **C11: PATIENT CAN create, CAREGIVER cannot**).
- `POST /api/campaigns/{uid}/submit/` — owner submits DRAFT → PENDING_VERIFICATION.
- `GET /api/admin/campaigns/verification-queue/`, `POST /api/admin/campaigns/{uid}/verify/` — `campaigns.verify` (SUP/ADM/VO).
- `POST /api/donations/` — **`Idempotency-Key` header required**; 10/hour/user + 2/min-per-campaign burst; replay → 200.
- `GET /api/donations/`, `GET /api/donations/{uid}/` — donor own unless `donations.view`.
- `GET /api/donations/{uid}/receipt/` — donor-only, COMPLETED-only (else 400).
- `GET /api/payments/`, `GET /api/payments/{id}/` — donor own unless `payments.view`.
- `POST /api/payments/{id}/retry/` — PENDING/FAILED only.
- `POST /api/admin/donations/{uid}/refund/` — SUP/ADM single-approval.
- `POST /api/webhooks/payments/{provider}/` — **no session auth; HMAC + TTL + allowlist**.

## 4. Security review

- **Webhook authentication (401); cross-cutting fix.** DRF's `APIView.handle_exception`
  coerces `AuthenticationFailed`/`NotAuthenticated` to **403** when the view has no
  `WWW-Authenticate` header — which is exactly the webhook's configuration
  (`authentication_classes=[]`). The gate therefore saw 403 instead of 401. Fix:
  `WebhookSignatureError(APIException, status_code=401)` raised by
  `PaymentWebhookAccess` for bad signature / stale timestamp / IP not allowlisted.
  Unauthenticated bad-signature calls now correctly return **401**, matching
  api-design §31.
- **Idempotency, end to end.** Donate replay (same key + donor → 200, same row),
  cross-donor key reuse → 409; webhook confirmation idempotent by unique
  `provider_ref` (terminal duplicates are audited no-ops reducing campaign silently
  is impossible); refunds can't double-approve a COMPLETED donation.
- **IDOR-safe detail:** donation objects are donor-scoped (foreign uid → 404), and
  receipts are donor-only and only for COMPLETED. Campaign detail enforced at
  queryset level → non-public, non-owner → 404.
- **Redaction (BR-009 / G4):** `provider_ref` only for `payments.view` roles
  (SUP/ADM/FIN/ORG); donors always see **`redacted_ref`** (`…` head/tail mask —
  verified no `SANDBOX-` prefix leaks). Receipts never contain provider refs.
- **Rate limits** on donation create/retry; per-campaign burst protects a single
  campaign from donation spam.
- **Audit:** initiate/retry/confirmed/refund/approve events recorded with action
  codes (`payments.initiate`, `payments.confirmed`, `payments.refund`, …);
  `resource_id` is `bigint` (integer PKs or None — never UUID strings).
- **Notifications:** confirmed payment informs the donor via the central service
  with a generic PAYMENT body (no amount/ref — G4 preview privacy).

## 6. Documented decisions / discrepancies (no silent divergence)

1. **403-vs-401 webhook mismatch (discrepancy, fixed in code).** api-design §31
   says unauthenticated webhook calls return 401; DRF's HTTP-401 coercion returned
   403. Fixed with the 401-status `WebhookSignatureError`; gate + tests lock it.
2. **`progress` serialized as a float**, not a string — Flutter parses both.
3. **Burst throttle period.** The approved "2/min burst" uses `2/min` because DRF
   `SimpleRateThrottle` has no `10min` period; the gate's 10/hour test and the
   hourly-limit widget/API tests use **10 distinct campaigns** so the per-campaign
   burst does not trip the hourly lanes (documented in tests).
4. **Receipt serializer is dict-based** (`{"donation": obj}`) — the
   `get_receipt_number` reads `obj["donation"]`, not an ORM attribute.
5. **`redacted_ref` mask** is `first4…last4` (verified against the `SANDBOX-`
   prefix leak); `provider_ref` remains a `payments.view`-gated raw value.
6. **Campaign visibility is queryset-scoped** for detail (404) with object-level
   ownership retained for writes; list is ACTIVE/CLOSED only (BR-007).
7. **C11 confirmations:** PATIENT may create campaigns; CAREGIVER may not
   (gate uses the CAREGIVER role for the denied-create check).
8. **Sandbox provider only.** M-Pesa uses the bundled `SandboxPaymentProvider`;
   the other four providers return a documented fallback ref. No live gateway
   credentials, webhook domains or TLS ingress were configured (see §7).
9. **`payments.verify` is service-internal** — the webhook path is gated by HMAC
   and there are **no role grants** for it (matching the matrix).
