## 2. What was delivered

- **Gatekeeper QA app (`backend/qa`)** — 68 behavioural/adversarial tests across
  eight modules (patients, emergency surface, auth surface, IDOR, privacy,
  transactions/webhooks, symptom catalog, end-to-end journeys). See the QA report
  for the full coverage matrix.
- **Adversarial verification.** Forced cross-user IDOR attempts on medical,
  blood, campaign, notification, medication-schedule, and access-grant resources;
  PII containment and 404s for inert `appointments`/`medical_records` surfaces.
- **Operational contracts pinned.** SOS **3/hour throttle → 429**, duplicate
  `Idempotency-Key` → **409**, emergency cancel scoping, M_PESA **webhook
  signature** path, symptom catalog seeding, public health endpoints — all
  asserted against real serializers/views/permissions/throttles, not mocks.
- **Real bug fixed with regression.** The suite caught `emergencies.views`
  raising `KeyError` when SAP SOS payloads omit `description`; fixed and covered
  so the original 500 cannot silently return.
- **Frontend contract suite (20 new tests).** Shell/navigation routing
  (5 destinations, SOS FAB, login → shell), offline → retry → recovery,
  `AuthController` token lifecycle (login, restore, refresh rotation, expired,
  logout), and form validation + real POST bodies (medication, profile, blood
  request) — all with `MockClient` over the real repositories/pages.
- **Stage gate** (`stage419_gate.py`) — one command that re-runs the entire
  evidence set (backend 433-suite, qa-only suite, mobile analyze + full test +
  stage419 files, `check`/migrations/pip) and reports `GATE_OK`/`GATE_FAILED`.

## 4. Risks & carry-over (no silent divergence)

1. **`qa` is test-only, but ships inside `PROJECT_APPS`.** It adds no models,
   migrations, or endpoints (management/commands is empty); its purpose is the
   gate harness. If desired later, it can move behind an environment flag — no
   runtime surface is exposed.
2. **LocMem/SQLite caveats.** Throttle state persists across test classes under
   the ephemeral profile, and user PKs reset per class; QA classes therefore
   `cache.clear()` in `setUp`. Production caching/settings are environment-owned
   (as established in 4.18 §4).
3. **Flutter offline tests use a failable `BaseClient`, not a real network
   conditioner.** They pin the *behaviour* (exception propagation, retry
   recovery, idempotency key) rather than device-level connectivity — a device
   smoke-runbook remains a deployment-time task.
4. **E2E depth.** Assertions cover one multi-step registered-patient journey;
   admin and staff journeys are covered at the surface/permission level, not as
   multi-page mobile flows. No scope creep into stage 4.20 (admin panel deep
   workflows) was taken.
