## 2. What was delivered

### 2.1 Integration suite & contract facts locked in from live behaviour

- **Envelope/correlation contract** (`ApiContractEnvelopeSuite`). Every
  success is `{"data": …, "meta": {"correlation_id": …}}`; every error is
  `{"error": {code, message, details, correlation_id}}`. Live probes pinned
  three facts the onboarding docs under-specified:
  - bad login password → **400 VALIDATION_ERROR** (not 401);
  - community reaction POST **and** DELETE both return **200**
    `{uid, reaction_count, reacted}` (not 201/204);
  - provider-webhook confirm returns an **enveloped** 200
    `{"data":{"status":"ok", …}}` (the global renderer applies to that view too).
- **Paginated vs plain lists clarified.** `CorePageNumberPagination` (DRF
  default) means access-grants, blood submatches, chat conversations, chat
  messages, medication events, education categories/content are paginated
  (`data.results`); symptom-types, notification devices, and blood-match feeds
  without a page claim stay plain arrays. The suite asserts the *correct parse
  for each endpoint* so the Flutter repos' mismatch risk is now test-proven,
  not guessed.
- **Cross-module consistency** (`CrossModuleConsistencySuite`): emergency
  validate→respond→resolve transitions + access-grant EXPIRED cascade +
  single-resolve single-notification; blood verify→run-matching→donor
  respond→accept locks the match; cancel cascades open matches to EXPIRED;
  community post+comment+reaction dedup; doctor chat start/self-block/read;
  education category + published-search; medication lifecycle + log-dose
  idempotency; profile patch + symptom timeline.
- **Failure injection** (`FailureInjectionSuite`): provider initiate outage,
  provider confirm accounting (campaign balance moves exactly once), refund
  double-guard (409), amount-mismatch webhook abort, forged-signature rejection
  (401) with no state change, disabled account losing API access immediately.
- **Concurrency & idempotency** (`ConcurrencyIdempotencySuite`): unique-constraint
  backed replays for log-dose/blood/emergency keys; donation key replay 200;
  cross-donor key reuse 409; campaign balance exactness.
- **Security denials** (`SecurityDenialsSuite`): PII never appears on donor/stranger
  blood surfaces; anonymous and non-owner requests rejected on
  health/data/notification routes.

### 2.2 Real bugs fixed (each with a shipped regression guard)

1. **Blood cancel left open matches live.** Cancelling a blood request left its
   open matches in SUGGESTED/NOTIFIED/ACCEPTED, and `respond_to_match` would
   still accept a response on a closed request. The cancel action now cascades
   open matches to EXPIRED; `respond_to_match` rejects once the request is no
   longer ACTIVE/MATCHING/MATCHED ("This request is no longer active.").

2. **`BloodRequest.perform_create` read the `Idempotency-Key` header but never
   persisted it.** Duplicate submissions with the same header key returned an
   extra 201 row instead of 409. The header key is now written to the row
   (`idempotency_key=key or None`), so the pre-check + the DB unique column
   both yield 409 on re-submission.

3. **A provider-initiate outage silently rolled back the failure record.** The
   service wrote a FAILED donation + `payments.initiate` FAILURE audit and then
   raised 503 — from *inside* the request's transaction — so the request-wide
   rollback erased the FAILED row and the FAILURE audit completely. The failure
   was invisible, unretryable, and unaudited. `initiate_donation` now
   materialises the FAILED donation + FAILED transaction + FAILURE audit
   outside the inner atomic, and the view catches the 503 while those writes
   commit: the client still gets a fail-locked **503 SERVICE_UNAVAILABLE**, the
   donor sees the FAILED attempt in history, and the failure is audited. A
   same-key retry replays the FAILED attempt without calling the provider again.

4. **Cross-principal reuse of one `Idempotency-Key` returned 400 instead of the
   documented 409.** Donations raised a DRF `ValidationError` (status 400) for
   "key in use by another donor". A 409 `IdempotencyConflict` now surfaces the
   documented CONFLICT without ever leaking the other donor's identity.

### 2.3 Test-infrastructure fixes (all test-side, none hide product risk)

The webhook harness needed its signed headers passed as WSGI `HTTP_` META keys
(the plain `APIClient` `**headers` spread surfaced empty header values and
produced false 401s), and `JsonAPIClient` gained a JSON-enforcing `delete()` for
body-carrying method calls. Field- and fixture-level mismatches in the suite
(reaction `user` field, `target_type` upper-case, `recorded_at` now(), search
token, expected statuses) were aligned to the verified API.

## 4. Risks & carry-over (no silent divergence)

1. **No physical Android device/emulator was available in this environment.**
   App verification remains widget-test + analyzer level (`flutter test` 85,
   `flutter analyze` 0). On-device/emulator acceptance (BT, sensors, network
   reachability, Play-side auth) is owned by the deployment runbook.
2. **`appointments` and `medical_records` remain inert scaffolds** (no models,
   no routes). They ship structurally but are NOT wired into the API — the
   Flutter app surfaces for them are stubbed. Reported honestly; deliberately
   out of scope for 4.x.
3. **Idempotency proof is constraint-backed and sequential.** On ephemeral
   SQLite the suite proves dedup through DB unique constraints (which the
   Concurrency suite asserts post-hoc). True shot-from-two-clients concurrency
   is a Postgres-deployment property and is not exercised in this harness;
   the constraint guarantees hold identically in Postgres.
4. **Provider-webhook 200 body is enveloped.** `PaymentWebhookView` sits behind
   the global `ApiEnvelopeRenderer`, so callbacks return
   `{"data":{"status":"ok", …},"meta":{…}}`. This is the documented system
   envelope; any 3rd-party provider carrier integration must tolerate/adjust
   for it in the deployment adapter layer.
5. **Provider outages still surface 503 to the client.** The FAILED attempt is
   now persisted and replayable, but Discoverability (the donor's history list
   showing the failure UI) is a Flutter-side follow-up owned by the app team.
6. **Live payment adapters are sandbox-only.** M-Pesa is a deterministic
   sandbox; all other carriers `FailbackProvider` fail closed. Wiring real
   carrier SDK credentials is a deployment-stage concern (unchanged from 4.17).
