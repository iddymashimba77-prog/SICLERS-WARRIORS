## 1. Scope

Deliver the approved notification surface: a **single central delivery service**
(STAGE_NOTIFICATION_04 model — there is deliberately no second "architectural
parallel-run" notification system; one service owns every emission), recipient-
scoped inbox + preferences API (Stage 4.8 foundation, §16), **push-device/token
registration** (api-design §21), **event-driven hooks** across the existing
modules, an **idempotent medication-reminder dispatch job**, and the **notification
center** mobile UI (§23). Suppression/CRO-friendliness, critical-class honours and
preview privacy (G4) are enforced server-side.

### 2.1 Notification types (approved §16 set — unchanged)

`MEDICATION_REMINDER · APPOINTMENT · BLOOD · EMERGENCY · PAYMENT · COMMUNITY ·
CONSENT · SYSTEM`. Every event below maps onto one of these; education, security
and chat events use `SYSTEM` (no new type was approved). Chat **message content
is never pushed** (Stage 4.10 decision) — only a conversation-started signal.

### 2.2 Endpoints (approved api-design §21 / matrix)

- `GET /api/notifications/` — recipient inbox, newest first, SUPPRESSED hidden, paginated.
- `GET /api/notifications/unread-count/` — `{unread: N}` (excludes SUPPRESSED/READ).
- `POST /api/notifications/{id}/read/` — mark one (IDOR-safe on foreign id).
- `POST /api/notifications/read-all/` — mark all visible.
- `GET /api/notifications/preferences/` — full category map, default-on.
- `PATCH /api/notifications/preferences/` — `{category, enabled}`; EMERGENCY → 400.
- `POST /api/notifications/devices/` — register/rotate push token (token write-only).
- `GET /api/notifications/devices/` — caller's devices.
- `DELETE /api/notifications/devices/{pk}/` — deactivate own device.

### 2.3 Event hooks (straight-line → central service)

| Source | Trigger | Type / priority | Recipient |
|---|---|---|---|
| `accounts/serializers.py` | login success → "New sign-in"; password reset → "Password change"; password change → "Password changed" | SYSTEM, `force=True`, HIGH | recipient |
| `community/services.py` | comment on post; new reaction | COMMUNITY (LOW) | post author |
| `education/services.py` | REVIEW approve → published; reject → rejected | SYSTEM | content author |
| `donations/services.py` | campaign approve/reject | PAYMENT | campaign owner |
| `doctors/services.py` | new conversation | SYSTEM | partner |
| `notifications/reminders.py` | periodic job | MEDICATION_REMINDER | schedule patient |

All bodies are **generic/privacy-safe** (no message text, no medication/diagnosis
names, no PHI); deduped via `delivery_key` (e.g. `community:comment:{pk}`,
`edu:published:{uid}`, `campaign:approved:{uid}`).

## 4. Security review

- **Recipient isolation:** every query is user-scoped; foreign notification ids and
  device ids return **404** on read/mark/deactivate (gate + tests).
- **Critical class cannot be muted:** EMERGENCY preferences are rejected (400) and
  EMERGENCY creation is always `force=True` CRITICAL. Security alerts
  (login/reset/password) are `force=True`.
- **Muting ≠ deletion:** muted events are stored as `SUPPRESSED` — auditable, but
  hidden from inbox and unread counts (CRO-friendly, no data loss).
- **Token hygiene:** push tokens are only ever accepted (write-only serializer);
  they are never returned on ANY endpoint. Tests assert the token string is absent
  from every device response.
- **Preview privacy (G4):** reminder bodies are de-identified and all hook bodies
  are free of message content and PHI; deep-link `data.route` is resolved through a
  client-side allowlist so a tampered payload cannot escape the app.
- **Idempotency:** `delivery_key` + DB uniqueness collapse duplicate reminder/event
  emissions, so the periodic job is safe to run daily/hourly.

## 6. Documented decisions / discrepancies (no silent divergence)

1. **One delivery service only.** The design's "architectural parallel-run" module
   (STAGE_NOTIFICATION_04) is intentionally **not** created: emitting events through
   a second provider would duplicate the approved `notifications` table and break
   suppression/unread/IDOR guarantees. The single `notifications.services` service
   is the documented owner.
2. **No new `Notification.TYPE`.** Education, security and chat events use `SYSTEM`
   (type list remains the approved eight). Chat pushes only a conversation-started
   signal, never message content (4.10 decision).
3. **Suppression is a status, not a delete.** Per §16 the status set already has
   `SUPPRESSED`; muted events keep the row for audit/recovery while being hidden.
4. **Security alert precedence:** login-success / password events are SYSTEM + HIGH
   + `force=True` so a muted SYSTEM category can never hide a security event (the
   ordinary mute flow still applies to routine system notices via `force=False`).
5. **FCM push is not wired.** `special-systems.md` §3.9.4 mandates push, but the
   codebase has no firebase/messaging SDK and a push provider without an approved
   runtime is out of scope. Device/token **registration is fully implemented** on
   both sides and `deliver_push(token, title, body)` exists as the documented
   extension point. Push is deferred, not silently dropped.
6. **Stage 4.12 bookkeeping completed (precondition, not feature work).**
   `donations` declared models (incl. `organizations`) but shipped **no migrations**,
   which made the ephemeral test DB unresettable (serialisation crash:
   `no such table: organizations`). To make regression gates honest we generated
   `donations/0001_initial.py` and replaced a non-serialisable `lambda` default on
   `Donation.transaction_ref` with a module-level callable. Additive, `sw_db`-safe,
   and later-stage feature-free; documented here so 4.12 reviewers have the diff.
7. **Appointment reminders deferred.** FR-APP-002 T-1d/T-2h reminders are
   integration points on the appointment domain model, which is still an empty
   scaffold in this codebase; `notifications/reminders.py` is their declared future
   home. No fake "appointment" event type was invented.
8. **PushDevice platform enum** (ANDROID/IOS/WEB/OTHER) pins the API contract the
   Flutter client mirrors; no offline queue until the provider is wired.
