## 1. Approved profile architecture (SSoT, quoted)

The approved identity ERD separates **authentication data** (User.account)
from **profile data** (1:1 `patients` row), never merged:

> `patients` | `user_id` FK unique (1:1), `date_of_birth`, `gender` CHECK,
> `genotype` CHECK (SS, SC, SBetaThal, SBetaC, unknown), `diagnosis_date`,
> `primary_diagnosis`, `emergency_contact_name`, `emergency_contact_phone`,
> `emergency_contact_relation`, `address_region`, `address_city`, `notes`
> (private), `created_at`, `updated_at`, `deleted_at` |  — database-design.md:162

Approved medical vocabulary is intentionally **minimal and fixed** (no invented
fields): `date_of_birth`, `gender`, `genotype`, `diagnosis_date`,
`primary_diagnosis`, `emergency_contact_*`, `address_region/city`. Every field
maps to an approved row/column; nothing beyond that set is collected.

## 2. Ownership / access policy (enforced server-side, §10)

- A user edits **only** their own `patients` row (1:1 via `user_id`).
- Doctors may view a patient's medical profile **only through the approved
  doctor↔patient relationship + consent** (§10 chain: auth → role → perms →
  relationship → consent → audit). Not automatic.
- Caregivers similarly gated by relationship + consent; never by default.
- Sensitive fields (`notes`, diagnosis detail) are private; audit logs record
  the **event**, not the medical content (§21).

## 5. Postgres switch-over (done — no database drop)

System PostgreSQL 18 (port 5432) was started and the app DB is now **the real
`sickle_cell`** (`config/settings/*`, `.env` unchanged: `sw_db_user@127.0.0.1:5432/sickle_cell`).

The pre-existing `django_migrations` history contained **default-auth cruft**
(from before `AUTH_USER_MODEL` became `accounts.User`) → `admin.0001_initial`
already-applied-but-`accounts.0001_initial`-missing, which Django reports as
`InconsistentMigrationHistory`. Because the stale tables were all owned by
`sw_db_user` and held **zero data**, they (and the migration history) were
cleared with plain SQL — no superuser, no `DROP DATABASE` required:

```sql
BEGIN;
DROP TABLE IF EXISTS auth_user, auth_group_permissions, auth_group, auth_permission,
  auth_user_groups, auth_user_user_permissions, django_admin_log,
  django_content_type, django_session CASCADE;
TRUNCATE TABLE django_migrations;
COMMIT;
```

then `manage.py migrate` applied everything fresh on Postgres (12 roles / 37
permissions seeded by `0003`+`0004`, incl. the approved `patients.*` codes and
`auth.profile_view`). Verified `manage.py check` → 0 issues.

### Auth fix surfaced by the Postgres smoke (login path)

Login on this project had never been exercised on a gate (both gates use the
JWT issued at **register**). Smoke found + fixed two real defects in
`accounts/serializers.py` `LoginSerializer`:
1. The base `TokenObtainSerializer` injects a required `USERNAME_FIELD`
   (`email`) field, so `/api/auth/login/` demanded BOTH `email` and
   `email_or_phone`. The injected field is now dropped in `__init__`.
2. It called `authenticate(..., email_or_phone=...)` which the default
   `ModelBackend` can never match. Login now looks up the unique
   `accounts.User` by `email__iexact OR phone__iexact` and verifies with
   `check_password`, then issues the access/refresh pair directly
   (`RefreshToken.for_user`), keeping uniform INVALID_CREDENTIALS /
   ACCOUNT_DISABLED semantics per API-design § `login`.

Re-run results after the fix: email login 200, phone login ✓, CAREGIVER
`/patients/me` 403, audit includes `LOGIN_SUCCESS`/`PROFILE_*`/`REGISTER`.
Ephemeral gates re-run → `GATE_OK` (both), no regression.
