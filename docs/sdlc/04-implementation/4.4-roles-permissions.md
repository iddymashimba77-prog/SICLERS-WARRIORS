## 1. Scope

This stage delivers the **server-side authorization layer** (the only place
access decisions are made — NFR-SEC-003/004, BR-002/003 §18, matrix "Deny
by default"). The client (Flutter) is a *consumer* of this layer; it never
makes an authorization decision, and hidden UI is defense-in-depth only.

Deliverables:
- Centralized **permission-class** set (`accounts/permissions.py`) that
  encodes the approved matrix gate per endpoint.
- **Account-status gating** that applies to *every* authenticated endpoint
  (ACTIVE / PENDING_VERIFICATION usable; SUSPENDED / DISABLED / DEACTIVATED
  rejected, §17/§18/§20).
- **Deny-by-default** role/permission assignment: server never trusts a
  `role_code`/`permission_code` from the request body; privileged roles are
  never self-registerable (§18 privilege escalation).
- Seed migration `0003` (authoritative role+permission+matrix rows) so a
  fresh/empty DB — the approved §32(a) path — has a coherent RBAC graph
  before any registration can bind a user to a role.
- `/me` + registration/login endpoints that return **role_codes /
  permission_codes** so the Flutter role-aware shell can route on real,
  server-issued claims (§23, matrix "SS UI-navigation contract").

NOT in scope (Stage 4.5+): object-level ownership enforcement on medical
records, consent-scoped access (C2), MFA assertion flow.

## 3. Enforcement rules (approved SSoT)

1. **Deny by default.** Unknown/missing permission → 403. Coarse
   `AllowAny` may appear only on `register` and `login`; nothing else.
2. **Status gate is a precondition.** Every authenticated endpoint first
   checks `account_status`; a `SUSPENDED`/`DISABLED`/`DEACTIVATED` account
   cannot read `/me` or any other protected view even with a valid token.
3. **Server-owned privilege.** `role_code` in `register` body is validated
   against `SELF_REGISTERABLE_ROLES`; attempting `SUPER_ADMIN`, `ADMIN`,
   `DOCTOR`, `VERIFICATION_OFFICER`, etc. via self-registration is rejected
   400 (§18) and logged as a `SecurityEvent`.
4. **Claims, not columns.** Role connection is M2M (`user_roles`), never a
   column on `User` (§4/§6, matrix "no bleeding into identity"). Permission
   codes are always read via the role join — object request carries nothing.
5. **/me is the SS contract.** `GET /api/auth/me/` returns uid, email,
   phone, account_status, role_codes, permission_codes — the *only* input the
   Flutter shell uses for role-aware navigation (4.4 §5 below).

Verified gate (ephemeral SQLite, `stage44_gate.py`):
```
register PATIENT:      201 + access/refresh issued
/me:                   200 (email, account_status, role present)
self-reg SUPER_ADMIN:  400 (privilege escalation rejected)
self-reg DOCTOR:       400 (privilege escalation rejected)
```

## 4. Object-level + account-ownership guards

Ownership/consent checks (your-password-change, your-own reset, your-own
/me) are enforced server-side with object-scoped serializers operating
**only** on `request.user`, never on a client-supplied `uid`:

- `ChangePasswordSerializer` / `PasswordResetConfirmSerializer` mutate only
  the authenticated/one-time-token-bound user.
- `MeView.get_object()` returns `request.user` unconditionally.
- Reset-request uniformly returns 202 (no account-existence leak, NFR-SEC-007).

## 5. Flutter developer contract (role-aware navigation)

`apps/mobile/lib/features/auth/data/auth_repository.dart`:
- `getRoleCodes()` returns `List<String>` from `/api/auth/me/` `role_codes`.
- `getPermissionCodes()` returns `List<String>` from `permission_codes`.

`lib/.../presentation/controllers/auth_controller.dart`:
- role-aware state uses `AuthRole.*` (PATIENT, CAREGIVER, …) plus the
  approved UI-shell gating: show role-appropriate navigation **and** request
  server enforcement (hidden UI ≠ authorization, NFR-SEC-018).
