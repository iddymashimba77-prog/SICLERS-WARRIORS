# AUTH-2 — Public Signup, Email Verification, Login & Role-Based Routing Implementation Report

> AUTH-2 delivers the public signup → email-verification → login → role-aware
> routing flow end-to-end (FR-AUTH-004/005, AUTH-005/006, §18 role-based
> routing; api-design §84–85, api-endpoint-matrix §36–37,
> mobile-screen-inventory AUTH-004..006, mobile-navigation §27). It builds on
> the AUTH-1 identity/verification architecture: signup is **restricted to the
> self-registerable roles** (PATIENT/CAREGIVER per `0003_seed_roles_permissions.py`
> and `REGISTER_SHORTCODES`), email verification is implemented with **single-use
> one-time tokens** (never stored raw), a freshly registered account stays
> `PENDING_VERIFICATION` until the code is consumed, and every post-auth route is
> decided by **server-asserted roles + verification state** — never inferred from
> a client-chosen account type. **No commit was made** (repo has 0 commits and
> stays that way). No database was created/reset beyond the ephemeral test DB.
> No new runtime packages. `verify/phone` remains a documented pending item
> (same token machinery — see §7).

## 1. Scope & Backend Gaps Closed

The approved surface already specified `POST /auth/verify/email` (FR-AUTH-004)
but the backend had **no implementation**: `verify/` was an alias of the login
view, `OneTimeToken(purpose=EMAIL_VERIFY)` existed but nothing consumed it, and
new users were stuck `PENDING_VERIFICATION` forever. AUTH-2 adds a minimal,
authorized surface (matches api-design §84 and the endpoint matrix §36):

- **POST** `/api/auth/verify/email/` — consume the single-use token; `204` on
  success, uniform `400` on invalid/expired, idempotent for ACTIVE accounts.
- **POST** `/api/auth/verify/email/resend/` — re-issue with a 5-minute cooldown;
  **uniform `202` for both unknown and real accounts** (no enumeration), never
  issued for ACTIVE accounts.

Security events gained `EMAIL_VERIFY_ISSUED`/`EMAIL_VERIFIED` kinds
(`accounts/models.py` choices only → `0012`), matching the precedent set by
`0005..0010`. Two new SecurityEvent rows plus a `create_notification` dev-channel
delivery are written for every issue/consume. The token is stored hashed
(receipt/plaintext stays client-side only), TTL 60 minutes, single-use.

## 2. Signup (Self-Registrable Roles Only)

`RegisterSerializer.create` assigns the requested role (validated against
`REGISTER_SHORTCODES = {PATIENT, CAREGIVER}` — `Doctor`, `Hospital`,
`Organization`, `Blood Donor`, and the privileged roles are **not** registrable;
the client never sends an un-registrable `role_code`), records `REGISTER`, issues
the identity-bound JWT pair (broker gates on `account_status`, so the tokens are
harmless while `PENDING_VERIFICATION`), then — if and only if the fresh account
is `PENDING_VERIFICATION` — issues and delivers the email-verification token and
reports `email_verification_pending: true` + `verify_token` in the response.
An ACTIVE account (e.g. legacy proviso) gets no token.

The mobile **signup page offers the seven public purposes** (Patient/Sickler,
Caregiver/Family, Blood Donor, Financial Donor, Doctor, Hospital/Clinic,
Healthcare Organization) with **honest messaging**: only Patient and Caregiver
are presented as self-registerable; Doctors, hospitals/organizations, and donors
get a guidance sheet explaining that verified onboarding issues those accounts
("account type is not verification"). After a successful register the app routes
straight into the **email-verification page**.

## 3. Email Verification (AUTH-005/006)

- `EmailVerifyView` (`POST /verify/email/`) consumes the token: hashed receipt
  lookup, single-use flip, `PENDING_VERIFICATION → ACTIVE`, `EMAIL_VERIFIED`
  event + notification, `204`. Invalid/expired/already-used → uniform `400`
  (no oracle). Already-ACTIVE accounts are accepted with `204` (idempotent).
- `EmailVerifyResendView` (`POST /verify/email/resend/`) — uniform `202`, 300 s
  cooldown keyed on the token store, only for non-ACTIVE accounts.
- `_issue_email_verify_token` / `_deliver_email_verify` are shared helpers in
  `accounts/serializers.py` reused by registration and the resend view.
- Mobile `AuthController.verifyEmail`/`resendEmailVerification` plus the
  `EmailVerificationPage` (`/verify-email`): inline entry of the code, inline
  invalid/expired errors, rate-limited resend action, and a success flow straight
  to login. The code is never logged or persisted client-side.

## 4. Server-Asserted Verification on Sessions (me + login)

`UserSummarySerializer` now carries the AUTH-2 verification subset alongside the
safe identity: `is_verified_doctor` (DOCTOR role + ACTIVE + APPROVED profile),
`doctor_verification_status`, and `facility` (`{uid, name, facility_type,
is_verified}`). Both `/auth/me` and the login response expose them, so the client
routes from **server truth only**; `login` returns `PENDING_VERIFICATION` status
for gated accounts.

## 5. Role-Based Post-Auth Routing (mobile)

New **`SessionRouter`** (unit-tested) resolves a session to exactly one
destination or a "Continue as" selection:

| Session (roles + state) | Destination |
|---|---|
| ADMIN / SUPER_ADMIN | `/admin` |
| DOCTOR **APPROVED** | `/doctor-shell` |
| DOCTOR PENDING/REJECTED/SUSPENDED/absent | `/doctor-status` (verification screen — never the clinical dashboard) |
| BLOOD_DONOR | `/donor-shell` |
| CAREGIVER | `/caregiver-shell` |
| PATIENT / SICKLER | `/shell` (five-tab patient shell) |
| HOSPITAL / HEALTHCARE_STAFF / ORGANIZATION | `/org-status` (facility identity + verification) |
| >1 context | `/continue-as` — no role silently dropped |

`AuthGate` (`/gate`, new `initialRoute`) replaces the old
`onGenerateInitialRoutes` heuristic: cold start shows a splash while the session
store is probed and validated against `/auth/me`. A stored-but-dead session never
opens a shell: `/me` `401` clears tokens → Public Home; a network failure lands
on Public Home **keeping** the tokens for silent retry; no token → Public Home.
`routes['/']` is preserved so the public home stays the shell root and
sign-out's `pushNamedAndRemoveUntil('/')` keeps working. Login and signup now
navigate through the router; multi-role login stops at a "Continue as" selector
instead of dropping roles.

The doctor and organization status screens (`/doctor-status`, `/org-status`)
explain the exact server-asserted state and offer sign-out / home, so a pending
professional has an honest surface rather than a fabricated dashboard.

## 7. Remaining Issues & Caveats

- **`verify/phone` (FR-AUTH-004 phone channel)** is documented but not
  implemented; the email token machinery is the template. Emergency/blood-donor
  identity works today only via email verification (`mobile-api-traceability.md`
  line 19 still marks it pending).
- **Organization membership** remains facility-operator-based (`Facility.operator`
  + `is_verified`), surfaced through `/org-status`; there is no standalone
  membership/affiliation model (AUTH-1 caveat stands).
- `restoreSession` treats a non-expiry server rejection (e.g. 403) as signed-out
  and clears tokens — deliberate and consistent with "never open shells on a
  dead session".
- Email delivery is the existing dev channel (`create_notification`); production
  SMTP/Twilio is out of scope for this report.
- `verify/email` is rate-limited at the uniform 202 level; the consumed-token
  check prevents replay.
