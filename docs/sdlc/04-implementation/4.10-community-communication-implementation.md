## 1. Scope

Deliver the community and private-communication surfaces defined by the approved
design, reusing the existing foundation (auth, permission codes, audit,
notifications, reference role model, Flutter API client/repositories).

- **Backend:** new `community` app (posts, comments, reactions, reports,
  moderation) and chat models + API added to the existing `doctors` app (per
  database-design row 74, which places `conversations`/`messages` in the
  doctor-domain).
- **Flutter:** community feed, post detail, post composer, conversation list and
  conversation thread; Messages route registered.

No duplicate models, permission codes, notifications, audit helpers, API
envelope or Flutter repositories were introduced.

## 4. Security review

- **Deny by default:** community reads = authenticated members; writes gated by
  permission codes; moderation endpoints moderator-only. Chat querysets are
  membership-scoped — a non-participant (including ADMIN, who holds no
  `chat.*`) receives **404**, authenticated-without-code **403**, anonymous
  **401**.
- **C13b honoured:** chat creation requires a verified professional
  (`is_verified_doctor`); `DOCTOR_PATIENT`-only conversation type enforced.
- **Privacy:** author/sender projections expose `uid` + `display_name` only;
  message-body previews are never returned by the conversation list (unread
  counts only); `add-participant` is denied for `DOCTOR_PATIENT`.
- **No E2E claim:** v1 relies on server-side ACL + TLS per §23; the UI makes no
  end-to-end-encryption claim.
- **Injection defence:** all user HTML is allow-list sanitized on write
  (`sanitizers.py`), verified in the gate (`sanitized: True`).
- **Abuse controls:** community post/comment/reaction 30/min, reports 30/min,
  resolve 60/hour, chat create 60/min, chat send 60/min (§29).
- **Content integrity:** reports are metadata-only; moderation hides before
  removing; message deletion tombstones and masks the body.

## 6. Documented decisions / discrepancies (no silent divergence)

1. **Education (FR-EDU) deferred.** Not part of the approved 4.10 endpoint
   matrix rows implemented here; carried forward to a later stage rather than
   invented.
2. **Attachments: schema only.** `MessageAttachment` exists for schema
   completeness (database-design), but no upload/list endpoints were built —
   there is no approved secure-storage pipeline. This is recorded as the
   security-api-traceability gap **ASG-6**.
3. **Blocking not implemented** (FUTURE v2, security-design §23). Participant
   `BLOCKED`/`REMOVED` statuses are modelled but have no endpoint.
4. **No message notifications.** The approved `Notification.TYPE` set has no
   `MESSAGE` value, so none were invented; the UI surfaces unread counts.
5. **No real-time/WebSocket.** The approved design is REST-only; polling/refresh
   is used instead.
6. **Permission naming reconciliation.** The 4.10 seed uses the role-permission
   matrix names (`community.create_post`/`comment`/`report`/`moderate`). The
   earlier `community.content.moderate` seeded by `accounts/0003` is left in
   place (not deleted) but is no longer referenced — flagged for cleanup.
7. **Reaction type is permissive** (max 20 chars, default `LIKE`, no DB CHECK)
   because the approved schema defines no constraint.
8. **Legacy `/api/v1` illustrative paths** were not used; the monorepo
   convention `/api/` (no version namespace) is followed.
