## 1. Scope

Deliver the approved AI surface **backend-only**, exactly as designed:

1. **`POST /api/ai/chat/`** — a single educational + decision-support assistant
   turn, gated by `ai.use` (granted **A to all 12 roles**, §3.21), covering
   FR-AI-001 (AI-assisted health education), FR-AI-002 (non-diagnostic
   informational assistance; BR-010/011) and FR-AI-006 (explicit non-diagnosis
   disclaimer).
2. **`GET /api/ai/trends/{patient_uid}/`** — FR-AI-004 health-trend analysis over
   the **owner's own** eligible patient-generated data (medications + adherence,
   symptoms, health timeline), gated additionally by `analytics.health_trends`
   and strictly **self-only**.
3. A **deterministic safety layer** (emergency escalation + guardrails) that runs
   *before* and *after* the provider (§3.9.5 pipeline), with **no transcript
   persistence** — AI activity is audit-metadata only through the existing
   `audit_logs` (traceability TC-AI-003), because the approved database-design
   contains **no `ai_*` entity** (see §3 and §8 for the justification).
4. A **provider abstraction** whose only shipped implementation is the
   **rule-based sandbox** (`settings.AI_PROVIDER = rule_based`, no external keys).
   External LLMs are the documented extension point and are **NOT configured**.

Explicitly out of scope (logged in §7/§8): external LLM providers, validated-ML
risk indicators (FR-AI-005 — no validated models + clinical governance exist),
cross-patient / DOCTOR / CAREGIVER personalization (consent surface is a separate,
unbuilt stage; ODD-8 default: patient-only), auto-creation of SOS requests by the
assistant, and any Flutter AI screen (MD-11 marks the assistant **FUTURE/hidden**).

## 2. Backend (`backend/ai_assistant`)

| File | Detail |
|---|---|
| `providers.py` | `BaseAIProvider` interface; `ChatPayload` (provider-independent request carrying only *server-assembled* authorized context + approved-knowledge snippets — never free-form client "context"); `AIResult`; **`RuleBasedProvider`** (deterministic, offline templates per use case, `model_id="rule_based"`); `get_ai_provider()` factory reads `settings.AI_PROVIDER`, fails honestly (`ProviderUnavailable` → 503, audited) on any unsupported name — never silently swaps models; `ProviderUnavailable(APIException)`. |
| `safety.py` | Rule-based (never LLM-dependent) safety layer. `EMERGENCY_PATTERNS` (loss of consciousness, breathing difficulty, severe chest, uncontrolled bleeding, neuro signs incl. seizures, self-harm) → `scan_emergency` short-circuits input to `EMERGENCY_RESPONSE` (refer Straight to Emergency/SOS + local emergency services; **never diagnoses, never auto-acts**). `_INPUT_GUARDS` refuse diagnosis / prescription / dose-change / stop-medication / fabricate-records / privacy-bypass / instruction-override requests with dedicated templates. `_OUTPUT_FORBIDDEN` + `validate_output` strip diagnosis claims, dosage numbers, certainty ("guaranteed/cure"), fabricated outcomes and privacy leaks (`SAFE_FALLBACK`). |
| `knowledge.py` | FR-AI-001 grounding: deterministic keyword retrieval over **PUBLISHED** `educational_content` only (title/body/category), bounded snippets (`settings.AI_KNOWLEDGE_SNIPPET_CHARS`), returns `uid/title/snippet` citations. Honest, simple retrieval — **not** an external RAG/vector service (none exists). No match ⇒ no source, and the assistant never pretends a source was used. |
| `context.py` | AD-7 minimum-necessary context. Assembles **own patient-generated data only** (adherence via `medications.services.adherence_stats`, symptoms, health-timeline — caps in settings), for personalized use cases only and only when the caller is a verified patient. ### 2.1 Endpoints

- `POST /api/ai/chat/` — `{message, use_case, personalized?, metric?}` →
  `{assistant_id, use_case, personalized, emergency_action, emergency_categories,
  safety{blocked,reason}, metrics?, sources[], context_used, limitation?,
  message, disclaimer}` (FR-AI-001/002/006).
- `GET /api/ai/trends/{patient_uid}/?window_days=1..90` →
  `{patient_uid, window_days, measured_at, metrics{medication_adherence,
  symptoms_recorded, symptom_pain_peak, symptom_pain_avg_10,
  health_timeline_events}, explanation, disclaimer}` (FR-AI-004; owner-only).

## 4. Security review

- **Non-diagnostic by construction.** BR-010/011 + healthcare-safety rules: the
  input guard refuses diagnosis/prescription/dosage/stop-medication requests *before*
  any provider runs; the output validator strips such claims *after*; the
  response always carries an explicit disclaimer (FR-AI-006).
- **Emergency is refer-and-stop.** Emergency intent is caught deterministically,
  returns a professional-care referral, is audited, and **never** auto-creates an
  SOS request or offers a diagnosis (tested: zero `EmergencyRequest` rows created).
- **Own data only, minimum necessary (AD-7).** Context is built server-side from
  the caller's own patient-generated data only — no full medical record, no
  genotype, no other person's data, and never client-supplied context. Non-owners
  receive general education plus an explicit limitation notice.
- **No persistence of conversation content.** No transcripts, no generated-text
  storage; AI events are audit-metadata only (append-only), matching the approved
  database-design (no `ai_*` table) and TC-AI-003/BR-012.
- **Provider honesty.** Only `rule_based` is configured; an unsupported provider
  name fails closed (503 + audited `ai.provider_failure`) rather than silently
  switching models. No API keys exist anywhere in settings/env.
- **Bound the cost surface.** Chat 6/min and trends 30/hour per user (AD-9
  documented limits); suspended accounts 403; every authenticated denial audited.
- **No footprint from the feature itself** — no new columns, no data mangling,
  no `ai_*` schemas; additive backend only.

## 6. Documented decisions / discrepancies (no silent divergence)

1. **`/api/ai/…`, not `/api/v1/ai/…`.** The stage brief repeats the design's
   `/api/v1` prefix, but **every implemented stage** (4.8–4.14) mounts under the
   established project convention `path("api/", …)` in `config/urls.py` (4.14
   made and documented the same choice). The endpoints are the AD-2 surfaces —
   the prefix is a routing detail, so project convention is kept and recorded here.
2. **One chat endpoint with a `use_case` switch, not six endpoints.** The
   requirements describe six distinct assistant use cases; api-design AD-2
   specifies a single `/ai/chat/`. Redundant endpoints are explicitly discouraged
   (§22), so one endpoint carries the whitelisted `use_case` field.
3. **No new database tables.** The approved database-design has no `ai_*`
   entity; the stage therefore persists **nothing** and audits via `audit_logs`
   only. This is the stronger reading of "the assistant must be auditable"
   (BR-012) and 4.14's identical stance on placing AI events in the existing
   audit system.
4. **Trends is owner-only even though SUP/ADM/DOC/CAR hold `analytics.health_trends`**
   — those grants are C2/C3/C4 (own/consented data), and with consent unmodelled
   a non-owner call is 403 `consent_unavailable` + audit. Documented in §2.2.
5. **`symptom_assistance` returns a structured journal draft and never writes
   `symptoms` rows** (§26: the assistant does not modify medical records);
   `health_summary` says exactly "The available records do not contain enough
   information…" when nothing eligible exists; `insight_explanation` explains the
   deterministic adherence figure only.
6. **503 service-unavailable error code.** The project error envelope had no 503
   row; `core/handlers._ERROR_CODE_MAP` gained `(503, None) → SERVICE_UNAVAILABLE`
   so provider unavailability is a stable machine-readable code like every other
   status.
7. **`ai.use` denial audit excludes account-status denials** (suspended → 403
   without an `ai.use_denied` row), identical to the analytics permission
   convention — status denials are not permission denials.

## 8. Not implemented because not approved

1. **External LLM / commercial AI provider integration** — not approved, no keys
   exist; `rule_based` sandbox is the configured provider.
2. **FR-AI-005 risk indicators / predictive alerts** — design requires *validated
   models with clinical governance*; there are none.
3. **Cross-patient AI personalization & trends** — requires the approved consent
   stage (never built here); 403 `consent_unavailable` + audit.
4. **Auto-generated SOS/emergency creation by the assistant** — safety rules say
   refer, never act; no auto-creation (tested).
5. **AI writing to medical records ("symptom_assistance" is draft-only)** — §26
   prohibits the assistant from modifying records.
6. **Flutter AI assistant screen** — MD-11 marks it FUTURE/hidden; adding it
   would be an unapproved surface, so none was added (regression-only mobile).
