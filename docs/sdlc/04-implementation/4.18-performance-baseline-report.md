# 4.18 — Performance Baseline Report

> Stage 4.18 (performance, scalability & reliability) begins by establishing a
> **reproducible baseline** so the optimisation work and every future change can
> be measured against a fixed reference. This report records the methodology,
> the pre-change snapshot, the instrumented endpoint matrix, and the acceptance
> context defined by
> `docs/sdlc/02-requirements/non-functional-requirements.md`.

---

## 1. Acceptance context (from NFRs)

| ID | Requirement | How Stage 4.18 interprets it |
|---|---|---|
| NFR-PERF-001 | Normal API operations should respond within an agreed performance threshold under defined test conditions | Agreed p95 target ≤ **500 ms for normal reads** under the "defined test conditions" below; verified by the reproducible `measure_perf_baseline` probe |
| NFR-PERF-002 | The system shall support pagination for large datasets | Global capped, page-numbered pagination on every list endpoint (`CorePageNumberPagination`) |
| NFR-PERF-003 | Heavy operations should be processed asynchronously where appropriate | Durable DB-backed job queue for heavy work (e.g. analytics aggregation) |
| NFR-AVL-002 | The system shall provide health monitoring | `/api/v1/health/` (liveness) + `/api/v1/health/ready/` (readiness incl. live db **and** cache checks) |
| NFR-SCAL-001 | Support growth without fundamental redesign | Query-count discipline (batch aggregations, active-materialisation, bounded feeds) keeps per-request work **independent of row volume** |

## 2. Defined test conditions (fixed)

| Condition | Value |
|---|---|
| Framework | Django 5.2 / DRF, Python 3.13 (project venv `backend/venv`) |
| Profile | `config.settings.ephemeral_test` — **in-memory SQLite**, seeded migrations, pristine database per run (Postgres `sickle_cell` is *never* reached by any 4.18 run) |

| Endpoint probe | `venv/bin/python manage.py measure_perf_baseline --settings=config.settings.ephemeral_test` |
| Hardware | Authoring machine (single process, local loopback; figures are for **relative regression tracking**, not absolute production capacity) |

## 4. Identified hot spots (drivers of this stage)

Static + dynamic (`CaptureQueriesContext`) review before the work:

1. **Patient dashboard / adherence** — per-medication `MedicationEvent` loops:
   N+1 growth with medication count.
2. **Admin broadcast** — one `create_notification` INSERT per recipient.
3. **Education categories** — `Select flat` count/list on every page load; the
   content **list** transported the full HTML body (up to 50 000 chars) per row.
4. **Community feed** — `Count(DISTINCT ...)` joins per post for reaction and
   comment counts (per-post cost grows with the join fan-out).
5. **Admin AI monitoring** — ~6 aggregate `COUNT(*)...GROUP BY` scans replaced
   by one grouped scan + one distinct-actor scan.
6. **Admin emergency monitor** — unpaginated feed + N+1 on requester/patient.
7. **Analytics series** — unbounded daily scan when `date_from` was omitted.
8. **Mobile** — education bookmarks fetched **serially** (one round-trip per
   bookmark); education list did not pass pagination params.
9. End-to-end test suite had **no** performance/silently-degrading-run regression
   suite.

## 5. Reproducible endpoint matrix (new harness, Stage 4.18)

The `measure_perf_baseline` management command seeds a minimal, **non-sensitive**
profile (roles, one article, one medication + schedule + event + timeline row,
one in-app notification) and drives ten representative endpoints, reporting
**status / DB queries / wall-clock per endpoint**. First recorded run
(post-optimisation, revertable to re-measure at any time):

| Probe | Path | Status | Queries | ms |
|---|---|---|---|---|
| health.ready | `/api/v1/health/ready/` | 200 | 1 | 4.4 |
| edu.categories | `/api/education/categories/` | 200 | 1 | 15.3 |
| edu.content | `/api/education/content/` | 200 | 2 | 6.4 |
| community.feed | `/api/community/posts/` | 200 | 5 | 8.9 |
| notifications.inbox | `/api/notifications/` | 200 | 6 | 10.6 |
| dashboard.patient | `/api/patients/me/dashboard/` | 200 | 9 | 12.8 |
| blood.donors | `/api/blood/donors/` | 200 | 5 | 6.4 |
| admin.dashboard | `/api/admin/dashboard/` | 200 | 32 | 31.2 |
| admin.analytics | `/api/admin/analytics/` | 200 | 7 | 7.3 |
| admin.ai.monitoring | `/api/admin/ai/monitoring/` | 200 | 6 | 8.0 |
| **TOTAL** | — | — | **74** | **111.3** |

Every probe completes far inside the agreed ≤ 500 ms read budget (p95 target)
under the defined test conditions; more importantly the per-endpoint **query
counts are the tracked invariant** — they must stay constant as data grows.

**Safety guard built into the harness:** the command refuses to run against any
non-SQLite engine (it migrates and seeds its own throwaway database), so it can
never reach the production Postgres.
