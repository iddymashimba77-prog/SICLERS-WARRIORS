## 1. Approved authentication architecture used (no invention)

Design docs specify (and this implementation follows, never overrides):

* **Identity:** `email` (only) is the login identifier + unique; `phone` is
  optional, unique. `accounts.User.AUTH_USER_MODEL` is the approved custom
  user (§ `accounts/models.py:47`).
* **Token strategy:** JWT access + refresh (`djangorestframework-simplejwt`),
  **rotation on** with denylist on refresh-rotation (approved `SIMPLE_JWT`
  block in `config/settings/base.py:177`); refresh lifetime config-driven.
  Because the SimpleJWT `token_blacklist` app is intentionally **not**
  installed (§ .27 chose an in-app `TokenDenyList`/`OneTimeToken` model
  instead of the contrib blacklist tables), rotation + logout revocation are
  implemented with the project's own
  `accounts.TokenDenyList` (jti PK, FK user, expires_at).
* **Account statuses (approved enum, verbatim):** `ACTIVE`,
  `PENDING_VERIFICATION`, `SUSPENDED`, `DISABLED`, `DEACTIVATED`
  (`accounts/models.py:80-84`). Login rejects `SUSPENDED`/`DISABLED`/
  `DEACTIVATED`; `PENDING_VERIFICATION` authenticates but surfaces the
  pending-verification state to trigger email/phone verification (§16).
* **Roles:** self-registration is limited to **PATIENT** and **CAREGIVER**
  only (`SELF_REGISTERABLE_ROLES`); privileged roles (ADMIN/SUPER/DOCTOR/
  HOSPITAL/NGO/…) are **never** assignable through registration (§18 § C17).
  Exactly one initial role per account. Verified in tests.
* **Persistence (Flutter):** tokens are held via a `TokenStore` abstraction;
  production wiring uses `flutter_secure_storage` (Keychain/Keystore) — never
  `SharedPreferences`. Passwords are never persisted anywhere on-device.

## 3. Endpoint matrix (approved API design § 07)

| Method/path | Component | Auth | Notes |
|---|---|---|---|
| POST `/api/v1/auth/register` | RegisterView | Public | 201; PATIENT/CAREGIVER only; never privileged |
| POST `/api/v1/auth/login` | LoginView | Public | 200 {access, refresh, user}; status-aware |
| POST `/api/v1/auth/logout` | LogoutView | Yes | revokes refresh family (denylist) |
| POST `/api/v1/auth/refresh` | RefreshView | Yes | rotates; denylists old jti |
| GET `/api/v1/auth/me` | MeView | Yes | safe identity; never password/hash/token |
| POST `/api/v1/auth/password/change` | ChangePasswordView | Yes | current password required |
| POST `/api/v1/auth/password-reset/request` | PasswordResetRequestView | Public | uniform 202; no enumeration (§17) |
| POST `/api/v1/auth/password-reset/confirm` | PasswordResetConfirmView | Token | single-use, expiring, hashed |
| POST `/api/v1/auth/verify/*` | VerifyView | Public | one-time code; TTL |
| POST `/api/v1/auth/register` carry | OneTimeToken | Public | hashed, single-use, expiring |

## 4. Protected endpoints
Every non-public view requires `IsAuthenticated` (JWT bearer). Unauthenticated
→ `401 {error:{code:"UNAUTHORIZED",…}}`. Unauthenticated users cannot reach
`/me`, `/password/change`, `/logout`, `/auth/refresh`.

## 5. Rate limiting / lockout (§ 29/§ 30)
DRF throttling configured; login/register and all auth mutation endpoints are
throttled to prevent brute force. Failed-login `SecurityEvent`s are recorded
(audit § 28) with no plaintext credentials in logs.

## 6. Audit (§ 28) — recorded events
`SecurityEvent` covers LOGIN_SUCCESS/LOGIN_FAILED/LOGOUT/PASSWORD_RESET/
TOKEN_REFRESH/ROLE_CHANGE/MFA_* — verified via `.models` Kernel. No
passwords/tokens/OTP havehed in logs (only jti + timestamps; token stored
hashed only).

## 7. Verification (§ 16)
Email + phone verification via `OneTimeToken`: hashed token, single-use
(`used_at`), expiry (TTL), never returned in responses, delivery via the
approved service abstraction (safe dev implementation; real SMS/email provider
still to be provisioned — not configured, no real credentials used).
