## 1. Scope & Ground Rules

- Active application DB in dev: system PostgreSQL, DB `sickle_cell` (owner-run local).
  Production DB per 3.9 env catalogue must be a **separate** database (e.g.
  `sickle_cell_prod`) with its own least-privilege role — never the dev DB.
- The retained legacy cluster on port 5433 (`sw_db*`) and the local dev DBs are out of
  the backup/restore scope below (dev infrastructure, owner-retained).
- Never store credentials in this repo. Backups are encrypted with a KMS/secret-manager
  key referenced by name only.

## 2. Backup & Restore Plan (with RPO/RTO)

### 2.1 Objectives (aligned to 3.9 §27–§28)

| Metric | Target | Commitment |
|---|---|---|
| RPO (Recovery Point Objective) | ≤ 24 h target (≤ 1 h desired) | An encrypted logical backup at least daily; hourly during active releases |
| RTO (Recovery Time Objective) | ≤ 4 h | Restore procedure below, verified by periodic drill |

### 2.2 What is backed up

1. **PostgreSQL** — logical backup via `pg_dump` (or `pg_dumpall` for roles) of the
   production database. Volume is small (community app); logical backups are the
   simplest correct option for Phase 1 (3.9).
2. **Application secrets/configuration** — the `.env`/secret-manager values, never in
   the repository. Snapshot the secret store contents per release.
3. **Static/uploaded assets** — currently none exist (no `FileField`/`ImageField`
   models; receipts are row data and regenerable). If file uploads are added in a later
   stage, this section must be extended (object storage + versioning).

### 2.3 Backup procedure (production)

- Schedule (cron/timer on a host that can read the DB):
  - Daily 02:00 `pg_dump --format=custom -d <PROD_DB> > /backup/prod-$(date +%F).dump`
  - Rotate: keep 14 daily + 6 monthly; off-host copy to a separate storage bucket.
- Encrypt artifacts with the reference KMS key (name recorded in the secret manager, not here).
- Record each backup name, checksum and timestamp in a backup ledger (table or bucket manifest).
- Pre-migration backups (3.9 §13/§27, runbook Step 1): any schema-change release takes a
  dedicated `pg_dump` immediately before `migrate` and retains it ≥ 30 days.
- Verify: after every backup, run `pg_restore --list` against the artifact to prove it is
  readable and complete (quick integrity), plus a full restore drill per §5.

### 2.4 Restore procedure (RTO ≤ 4 h)

1. Provision/confirm the target PostgreSQL (same major version, ≥ same storage).
2. Create the least-privilege role and restore it (`pg_restore` recreates roles as needed).
3. `pg_restore --clean --if-exists --dbname=<PROD_DB> /backup/prod-YYYY-MM-DD.dump`
4. Verify row counts, latest `audit_logs`/`security_events` timestamps, and a known-good
   record (e.g. latest donation) match the backup ledger.
5. Point the application at the restored DB (env `DB_*`), run health `ready` check and the
   Stage-4 integration smoke suite before reopening traffic.
6. Declare data acceptable only after the verification; otherwise restore the next-newest
   artifact and retry.

### 2.5 Restore drill cadence

- A full restore drill into a throwaway database at least once per quarter, and within
  30 days before any production release (runbook Step 3 prerequisite). RPO/RTO claims are
  only valid when a recent drill has succeeded.

5. **Post-release** — new backup of the new state; release log entry (tag, SHA, DB version,

## 4. Rollback Plan

- Triggers (3.9 §29): health checks fail post-deploy, smoke tests fail on core flows,
  error-rate/latency above threshold > 10 min, data-integrity anomaly.
- Backend: point the reverse proxy back at the previous immutable image/tag (kept on host,
  §3 step 2). Backward-compatible schema releases roll back instantly with no DB work.
- Schema-changing releases follow the expanded/contract pattern (3.9 §13/§29): if migrate is
  not reversible, restore the pre-migration backup (§2.3) — accepting the documented
  data-loss window (RPO).
- Mobile: a bad app build cannot be force-rolled back on devices; release policy = staged
  Play rollout + keep previous Play release active until the new one is verified by a device
  smoke test (see report §22 — device checks still pending).
- Admin Web: redeploy previous bundle (once such builds exist).
- Re-verify: full runbook Steps 9–15 before declaring recovery.

## 5. Incident Response Plan

- Severity matrix:
  | Sev | Example | Response |
  |---|---|---|
  | S1 | Core API down / data loss / PHI exposure | Page owner; invoke rollback §4; preserve logs/audits; freeze releases |
  | S2 | Payment webhook errors / high error rate | Triage within business hours; sandbox re-test; hold release |
  | S3 | Cosmetic or minor anomaly | Next scheduled window |
- Channels: project owner is the single commander; emergency-wide documented approvals per 3.9 §2.
- Playbooks:
  - **API down**: confirm `health/ready` from the proxy; restart workers; if still failing, roll back §4.
  - **Data incident**: immediately take an encrypted full `pg_dump` of current state (evidence),
    then apply §2.4 restore if warranted; preserve `security_events`/`audit_logs` records.
  - **Security suspicion**: rotate `DJANGO_SECRET_KEY`, payment secrets and DB password; revoke
    tokens (all existing JWTs are invalid once the signing key changes); inspect audit log.
- Post-incident: record timeline, root cause, evidence, and remediation in the incident ledger
  and update this plan; a no-blame review within 7 days.

## 6. Disaster Recovery Readiness

- **Current status: NOT VERIFIED** — no off-site copy of any database exists today and no
  restore drill has run, so RPO/RTO are aspirational until §2.5 drills begin (Stage 5).
- Target posture for production:
  - Backups in a separate availability zone/provider from the app (§2.3 off-host copy).
  - DB promotion path: if the primary host is lost, restore the newest verified backup on a
    fresh host within RTO; DNS/proxy cut-over; repeat restore verification (§2.4).
  - Minimal DR stack = PostgreSQL + backend image + proxy config + secret store. No Redis
    dependency today (cache optional); keep that property unless explicitly accepted.
