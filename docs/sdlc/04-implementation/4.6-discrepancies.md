# 4.6 — Medication & Health Tracking: Design Discrepancies

> Stage: 4.6 (Medication + Health Tracking)
> Purpose: every intentional deviation from the approved (signed-off) system
> design, recorded with the mitigation taken. Style mirrors 4.3–4.5 gate logs.

## 1. `dose_logs` → `medication_events` (source table renamed in implementation)

- **Approved row:** `docs/sdlc/03-system-design/database-design.md` row **212** —
  `medication_events` (`schedule_id` FK, `patient_id` FK, `status`
  CHECK(TAKEN MISSED SKIPPED SNOOZED), `taken_at` null, `note`, `created_at`
  immutable; adherence derived).
- **Observed drift in earlier stage drafts:** the pre-4.6 scaffold shipped a
  `dose_logs` table with a `DELAYED` status that did **not** match the signed-off
  row-212 vocabulary.
- **Decision:** re-aligned to row 212. New model `MedicationEvent`
  (`medications/models.py`), DB table `medication_events`, status vocabulary
  exactly `TAKEN/MISSED/SKIPPED/SNOOZED`, `taken_at` nullable with a CHECK that
  forces `TAKEN ⇒ taken_at NOT NULL`, and an immutable `created_at`
  (overridden-create disabled). The old `dose_logs` table is dropped by
  migration `medications/0002_medication_events.py`. SNOOZED is the approved
  4th state (snooze is a "declared miss", not a "delay").
- Backward-compat aliases: the DB `DoseLog`→`MedicationEvent` rename surfaced in
  the imports; `DoseLogOutSerializer` is retained as a thin read serializer for
  events.

## 2. URL namespace `/api/` vs approved `/api/v1/`

- **Approved:** `api-design.md` uses `/api/v1/<resource>` consistently.
- **Implemented:** existing (4.1-era) `config/urls.py` mounts everything under
  `/api/` with **no `v1` segment**; 4.6 surfaces follow that in-repo convention:
  `/api/medications/`, `/api/symptoms/`, `/api/symptom-types/`,
  `/api/health-timeline/`.
- **Impact:** consistent with the already-shipped post-auth API surface
  (`/api/auth/*`, `/api/patients/me/*`). Reintroducing `/api/v1/` now would
  fork the client base URL for a single stage; recorded as a conscious deviation
  (same as 4.3/4.4).

## 3. Legacy (Stage 4.4) permission codes retained alongside the approved codes

- **Approved codes for 4.6** (`role-permission-matrix.md` §3.5, §3.6):
  `medications.create/view/update/delete`, `symptoms.create/view/analyze` —
  seeded by `accounts/0007_seed_medication_health_permissions.py`.
- **Pre-existing codes:** an earlier scaffold seed (4.4-era `accounts/0003`)
  created `medications.prescribe` and `symptoms.record` — these are **not** in
  the approved matrix. They are deliberately left untouched (removing them would
  churn unrelated role grants + the 4.4 contract), and deny-by-default still
  holds: a role only gains what its matrix cell grants. `symptoms.record` is
  referenced by the 4.6 gate as the view-create code for the legacy path.
- **`symptoms.analyze`:** seeded as a permission row with **zero** role grants —
  the approved matrix cells for it are analytic/consent-gated (C2/C3, later
  stage). Denied by default until the analytics stage.

## 4. Patient `medications.delete` — soft-delete interpretation

- **Approved matrix §3.5:** `medications.delete` = **D** for patient; the
  endpoint matrix (`/medications/{id}` DELETE) lists owner=owner.
- **Implemented:** `DELETE /api/medications/{uid}/` for the owner patient is a
  **soft-delete** (`deleted_at` set, `is_active=False`), matched to the approved
  data model (row 210 keeps `deleted_at` for pharmacist/audit trail) and to the
  FR-MED stop/suspend semantics. Hard delete is intentionally not offered to a
  patient (medical audit surface); `medications.delete` gates the owner-only
  stop action.

## 5. Schedules carry `uid` + `created_at` beyond row 211

- **Approved row 211:** `medication_schedules` | `medication_id` FK,
  `time_of_day` time, `days_of_week` JSONB, `notes`.
- **Implemented:** the model adds a unique `uid` (stable lookup key for
  `schedule_detail` and events) and `created_at`. Minimal, storage-only
  extension matching the pattern already used for `medications.uid` (row 210);
  the public API (time, days, notes) is untouched.

## 6. `health_timeline` implemented as a synchronous materialized projection

- **Approved row 219:** `health_timeline` — "materialized projection
  (`patient_id`, `event_type`, `event_id`, `occurred_at`, `summary`, `payload`
  JSONB) written by domain events; rebuild strategy documented for backfill"
  (DBD-2: "Materialize `health_timeline`… define rebuild/backfill job").
- **Implemented (4.6 scope):** a real `HealthTimelineEntry` table written
  **synchronously in the same transaction** as each domain write
  (medication start/update/stop, schedule removal, dose log, symptom record,
  pain record) via `services.record_timeline()`. This is the row-219 shape with
  the requested `(patient_id, occurred_at DESC)` index.
- **Deferred (documented, not skipped):** the **backfill/rebuild job** called for
  by DBD-2 (audit-log replay → timeline) is deferred to the analytics stage; the
  projection is currently append-on-write only. Any future backfill must
  de-duplicate by `(event_type, event_id)`.

## 7. Idempotency: header-first, body fallback (superset of approved)

- **Approved (`api-design.md` §30 / endpoint row 152 → `log-dose`):** body incl.
  `idempotency_key`, duplicate → 409.
- **Implemented:** `POST /api/medications/{uid}/log-dose` reads the
  `Idempotency-Key` **header** first, falls back to the body `idempotency_key`
  (both accepted — a strict superset of the approved contract). Duplicate →
  `409 IDEMPOTENCY_CONFLICT` (pre-check + DB unique-constraint race catch).
  The Flutter client always sends the header.

## 8. Adherence stats are synchronous in this stage

- **Approved (`api-design.md` FR-MED-006):** "`/medications/stats` … NFR-PERF-003
  async".
- **Implemented:** `GET /api/medications/stats` computes adherence on request
  (bounded 30-day window over `medication_events` + schedule expectations).
  Asynchronous computation is a performance concern for large detists; flagged
  for the analytics stage (mirror of the async ConsentRequest / reminders
  deferrals). Non-clinical supportive framing kept (§13) — no clinical claims.

## 9. Reminder push (FR-MED-003) intentionally not shipped

- **Approved:** mobile-ui-ux-review M4: "Reminder strategy (local scheduled vs
  FCM) unsettled (AD-MD-9) — decide before medication feature implementation". +
  Date-ambiguity in approved `schedule` model.
- **Implemented (4.6 scope):** the *data backbone* only —
  `MedicationSchedule` rows + `services.expected_slots()` (quantised,
  day-of-week aware dose-slot computation) which the future NotificationService
  will consume. No local timers, no FCM, no push claims. Decision AD-MD-9 stays
  open. (Explicitly NOT advertising reminder delivered-on-time as a stage
  deliverable.)

## 10. Dashboard provenience

- **Approved:** endpoint matrix row **74** — `GET /patients/me/dashboard` (own),
  "meds/appts/symptoms summary"). Implemented under `patients/urls.py`
  (`PatientDashboardView`) so the approved `/patients/me/*` namespace is kept,
  not `/medications/dashboard`. Appointments/upcoming-ointments on the card are
  deferred (appointments module is a later stage); the 4.6 dashboard covers
  meds + symptoms + adherence (the permitted subset).

## 11. Symptom records are append-only in this stage

- **Approved (§3.6):** only `symptoms.create`/`view` are patient-granted;
  there is no patient `symptoms.update/delete` cell.
- **Implemented:** `SymptomViewSet` has **no** update/delete routes
  (404/405 for PATCH/DELETE) — records are permanent clinical journal entries.
  Correction of a mis-entry is a documented follow-up on the medical-records
  surface (audited), not a free edit.

## 12. Test DB for `manage.py migrate` on Postgres (operational note)

- The ephemeral gates (`stage4{4,5,6}_gate.py`) run on in-memory SQLite with the
  `ephemeral_test` settings (`config/settings/ephemeral_test.py`). `postgres_smoke.py`
  exercises the **real dev** DB (`sickle_cell`, port 5432) and rolls back.
  `manage.py test` therefore must be invoked with
  `--settings=config.settings.ephemeral_test` (no CREATEDB privilege on the live
  Postgres, by design).

# AUTH-1 — Identity, Roles, Verification & Authorization: Caveats

> Addendum recorded at AUTH-1 implementation (Stage 4.x, post-4.24). Every
> intentional deviation from the signed-off design is listed with its mitigation.
> Full detail: `docs/sdlc/04-implementation/4.25-auth-1-implementation-report.md`.

## 13. Legacy verification/consent codes retained beside AUTH-1 codes

- **Pre-existing (4.4-era) permission rows** `consents.manage`, `consents.verify`
  and `verification.doctors.approve` / `verification.doctors.reject` are **not**
  in the approved matrix and carry **zero** AUTH-1 role grants. They are left
  untouched (same precedent as caveat §3 — removing them would churn unrelated
  4.4 grants). Every AUTH-1 gate uses the approved codes
  `doctors.*`, `caregivers.*`, `consents.*`; deny-by-default still holds because
  a role only gains what its matrix cell grants (migration `accounts/0011`).

## 14. Caregiver `DECLINED` is expressed as `REVOKED`

- **Approved (`database-design.md` §8.1):** `caregivers.status`
  CHECK(PENDING ACTIVE REVOKED EXPIRED) — there is **no DECLINED** value.
- Declining an invite therefore maps to status **REVOKED** (with `CAREGIVER_DECLINED`
  SecurityEvent + `caregivers.decline` audit row so the event is distinguishable),
  rather than inventing a non-approved status.

## 15. Consent `permission_scope` accepts 2-part legacy codes

- **Approved (`role-permission` §22):** permission codes are
  `module.resource.action` (3 parts) — e.g. `medical_records.view`.
- The shipped seed matrix contains legacy **2-part** codes (`patients.view`,
  `caregivers.modify`) that are already used as view gates. `ConsentCreate` /
  `ConsentPatch` / `CaregiverPermissions` validators therefore accept both
  2-part and 3-part dotted codes (`len(parts) in (2, 3)`); the scope is still
  validated against the compact code shape and enforced by
  `ConsentService.can_access`.

## 16. SecurityEvent names for verification decisions

- The approved traceability does not pin event strings; the implementation uses
  the declared tuple in `accounts/models.py` (migration `accounts/0010`):
  **`DOCTOR_VERIFICATION_SUBMITTED` / `DOCTOR_VERIFIED` / `DOCTOR_REJECTED` /
  `DOCTOR_SUSPENDED`** (approval is not "APPROVED"/"appeared" ambiguity — one
  verify endpoint decides approve *or* reject, action code `doctors.verify`).

## 17. Emergency override: audit action code `emergency.access_grant`

- The signed-off `SecurityEvent` kinds (`EMERGENCY_ACCESS_GRANTED` /
  `EMERGENCY_ACCESS_REVOKED`) exist, but the **operational** audit for the C10
  bounded grant reuses action code `emergency.access_grant` with
  `details.action ∈ {issue, expire, revoke}` (issue in
  `create_emergency`/`_ensure_grant`, expire on `resolve`, revoke on `cancel`) —
  the only approved `emergency.*` umbrella code; no new code was minted.

## 18. Unchanged/unresolved at AUTH-1 close

- **Organization membership** (roles `member` / `admin` table in the approved
  schema) is **schema-not-rendered**: the approved database referenced an
  org-membership table that has no model nor endpoint. Recorded, not built (no
  matrix cells / endpoints reference it).
- **DBD-5** (`doctors.verification_expires_at`): tracked, **not blocking** —
  enforced as approved (default null; no auto-suspension job).
- **Secure document upload pipeline** for `verification_documents` (signed
  initiate + complete, ASG-6) remains open: the verify endpoints accept
  secure-storage keys, no upload/read blob endpoint ships yet.
