## 1. Scope

Deliver the approved **1:1 patient medical-identity profile** behind
ownership + permission + audit gates:

- `patients` model — fields **exactly** row 162 (no invented fields),
  `gender`/`genotype` CHECK vocabulary fixed and server-validated.
- `GET/PATCH /api/patients/me` — owner-scoped (structural 1:1; no uid lookup
  on this surface ⇒ IDOR impossible by construction).
- `/me` contract upgraded to the 4.4-documented `role_codes` +
  `permission_codes` (the Flutter shell + profile screens route on these).
- Audited changes (`SecurityEvent` `PROFILE_CREATED`/`PROFILE_UPDATED`) with
  the **event only** — never the medical payload (§21).
- Role-aware Flutter **Profile** and **Medical Profile** screens with an
  edit flow; hidden UI ≠ authorization (backend gates remain authoritative).

NOT in scope (Stage 4.6+): full medical records/consents (C2), caregiver
consent graph, doctor↔patient relationships, blood-group donor profile,
health timeline.

Authentication data stays on `accounts.User`; medical identity lives in
`patients` — they are never merged (identity-access ERD, 4.5 §1). `blood_group`
is *not* here (it belongs to `blood_donors`, later stage) and is therefore not
collected on this surface.

## 4. Ownership / privacy policy (server-enforced)

- A user reads/writes **only** their own 1:1 row.
- Gate chain per request: auth → account-status → **is a PATIENT** → approved
  permission (`patients.view` for GET, `patients.update_own` for PATCH)
  → structural owner scope (`user_id == request.user`).
- CAREGIVER / DOCTOR / HOSPITAL / ADMIN never fall through to a patient row
  on this surface; cross-patient clinical access flows through the separate
  consent/relationship architecture (C2/3, later stage).
- `notes` is private: owner-visible in `/me` responses only; audit records
  the **event type**, never the content (§21).
