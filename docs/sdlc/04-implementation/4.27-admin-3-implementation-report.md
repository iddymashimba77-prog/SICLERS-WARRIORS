# ADMIN-3 — Admin Portal: RBAC Matrix, Review Directory, Donation Administration & Mobile Portal Implementation Report

> ADMIN-3 delivers the mobile admin portal end-to-end on top of the existing
> RBAC core: a **role & permission matrix admin API** for SUPER_ADMIN
> (`accounts/roles_views.py`), a **facility review directory**
> (`/api/admin/facilities/`), **donation financial administration** (summary,
> ledger, refund), and the **Flutter portal** — a permission-aware shell whose 15
> sections are rendered strictly from the `/me` `permission_codes` the server
> advertises. **Nothing is fabricated**: every portal section maps to a real
> backend endpoint, every action is re-enforced server-side, and deny-by-default
> is exercised by the caller's missing permission code, never the UI. **No commit
> was made for this stage** (the repo keeps its single pre-existing root commit
> `ef0dc68` untouched; nothing was committed here). No new runtime packages on
> either side; no production DB created/reset (ephemeral test DB only).

## 1. Scope & Backend Gaps Closed

The RBAC model, allow/deny override machinery and the DRF permission framework
already existed (AUTH-1/§4). What was missing was the **operational admin
surface** that consumes them. ADMIN-3 closes three backend gaps:

- **Role & permission matrix** — there was no way to *administer* grants:
  `GET /api/admin/roles/` (matrix), `GET/POST /api/admin/roles/{code}/permissions/`
  (read one role's codes, grant/revoke with an audited reason). Writes are
  **SUPER_ADMIN-only**, the SUPER_ADMIN kernel is lockout-guarded.
- **Facility review directory** — `FacilityListView` was public-only; there was
  no admin list (`/api/admin/facilities/`) separate from the verify action.
- **Donation financial administration** — campaigns had verification; donations
  had an owner ledger, but no admin ledger, summary, or refund endpoint.
  ADMIN-3 adds `GET /api/admin/donations/`, `GET /api/admin/financial/summary/`,
  and `POST /api/admin/donations/{uid}/refund/`.

Every denied/privileged decision is audited (`audit/services.py`) with the
requester, action code, resource and a mandatory human reason (min 5 chars).

## 2. Backend — Roles & Permissions API (`accounts/roles_views.py`)

- **`GET /api/admin/roles/`** — paginated matrix, one row per role with
  `permission_count` and `member_count` (live queries). Readable by
  SUP/ADM (`admin.roles.manage`); denied to VO/DOCTOR/PATIENT (403) and anon (401).
- **`GET /api/admin/roles/{code}/permissions/`** — the role's effective codes.
  Unknown role → 404.
- **`POST /api/admin/roles/{code}/permissions/`** — body
  `{permission_code, grant, reason}`; **SUPER_ADMIN-only**. Grant → 201,
  revoke → 200; duplicate grants / noop revokes / unknown codes → 400; reason
  required. Writes record `admin.roles.permission_grant` / `.revoke` audit rows.
- **Lockout guard** — the SUPER_ADMIN kernel
  (`admin.permissions.manage`, `admin.roles.manage`, `admin.users.manage`,
  `admin.audit.read`, `admin.audit.export`, `admin.system.manage`) can never be
  revoked (`400`), so an operator cannot accidentally orphan the last admin.
- **Privileged-role boundary** (C17, carried forward) — only SUPER_ADMIN may
  grant/revoke privileged role codes; ADMIN may assign only non-privileged codes
  and may never touch a privileged account. Self-assignment always denied.

## 3. Backend — Facility Review Directory

- **`GET /api/admin/facilities/`** — review directory behind `facilities.verify`
  (SUP/ADM/VO per `facilities/0002_seed_facility_permissions.py`). Paginated;
  supports `status` (verified/pending), `q`, and `facility_type` filters; rows are
  the operator-safe Facility serializer (no PHI beyond operating identity).
- **`POST /api/admin/facilities/{uid}/verify`** — registered **without a trailing
  slash**; reason is mandatory only when rejecting. Records `facilities.verify`
  audit + `ADMIN_ACTION` security event.

## 4. Backend — Donation Financial Administration

- **`GET /api/admin/donations/`** — paginated ledger (financial-donations admin
  scope, `donations.view` + SUP for refunds). Status filter; refunded flag.
- **`GET /api/admin/financial/summary/`** — KPI snapshot over the **confirmed
  ledger only** (`confirmed_donations_total/count`, `refunded_total`,
  pending/active/closed/verified campaign counts). Pending never inflates totals.
- **`POST /api/admin/donations/{uid}/refund/`** — `donations.refund`,
  **SUPER_ADMIN-only**; full or partial refunds of COMPLETED donations only,
  double-refund and non-terminal refunds rejected, campaign raised-amount
  counters adjusted, `donations.refund` audit row written.

## 5. Mobile — RBAC Session Contract

`AuthSessionOutcome` and `AuthController` now carry `permission_codes` parsed
from `/api/auth/me/` (`data/auth_repository.dart`, `auth_controller.dart`).
`/me` serializes **server-authenticated** `role_codes` + `permission_codes`
(`accounts/serializers.py`); the portal consumes exactly that, so a rebrand of
client-side role names cannot widen access — the codes come from the grants table.

## 6. Mobile — Admin Data Layer

- **`domain/admin_authz.dart`** — `AdminPermissions` constants (mirror of the
  seeded codes) + `adminSectionsFor(permissions, roles)`: the ordered, gated
  portal catalog. Sections render only when the session holds a matching code;
  **roles alone never open a section**.
- **`data/admin_models.dart`** — typed projections of the admin serializers
  (AdminUser, AdminRole, AdminDoctor, AdminFacility, AdminBloodRequest,
  AdminCampaign, AdminContent, AdminReport, AdminDonation, AdminFinancialSummary,
  AdminAuditLog, SecurityEvent, AiMonitoring, AdminDashboard, AnalyticsResult,
  AdminBroadcastResult). Parsing is defensive (missing keys → safe defaults).
- **`data/admin_repository.dart`** — typed client for the full admin matrix:
  envelope unwrap, pagination (`results`), Bearer auth, and `_errorFrom` carving
  the DRF error envelope. `changeUserRole` uses raw `http.Request` for the DELETE
  verb; `verifyFacility` deliberately uses the no-trailing-slash URI that the
  backend route requires.
- **`presentation/widgets/admin_widgets.dart`** — `AdminAsyncList` (+ public
  reloadable state), `AdminStatusChip`, `AdminSectionHeader`, `confirmAction`,
  `promptReason` (min 5 chars), `showAdminMessage`.

## 7. Mobile — Portal (Shell + 15 Sections)

`shared/widgets/admin_shell.dart` builds a collapsed navigation rail (drawer on
narrow phones) from `adminSectionsFor`, an `AppTopBar` identity banner, and a
body switch keyed on section label — all backed by real endpoints:

Dashboard (live KPI grid), Users (status/search + roles grant/revoke dialog),
Doctors (verification queue approve/reject/suspend), Organizations (review
directory + verify w/ no-slash URL), Blood Verification (queue verify/reject),
Campaigns (queue + pause/close), Roles & Permissions (matrix + SUP-only
permission chips), Content Review (education approve/reject + preview),
Moderation (reports resolve NONE/HIDE/REMOVE / dismiss), Finance (KPI summary +
ledger + SUP refund), Broadcast (ALL/ROLE/USERS with `user_uid` list), Audit Logs
(filters + detail), Security Events (filters + detail), Analytics (metric +
DAILY/WEEKLY/MONTHLY), AI Monitoring (KPI grid + by-action). Disabled states are
honest: non-SUP users see Roles read-only and no refund path; every mutation
re-validates server-side.

## 9. Remaining Issues & Caveats

- **Platform settings / feature-flag screens** are not a backend subsystem in
  this build; the portal therefore ships no fabricated "settings" section — the
  flagged items remain documented as missing dependencies (identify-don't-invent).
- **Blood run-matching** (`POST /api/admin/blood/run-matching/`) exists server-side
  but has no portal page; running it from a UI is deferred (not part of the
  approved portal inventory).
- The mobile client must agree with the server on the no-trailing-slash facility
  verify route — enforced in repository + pinned by test; a future backend rename
  would break that single contract point loudly.
