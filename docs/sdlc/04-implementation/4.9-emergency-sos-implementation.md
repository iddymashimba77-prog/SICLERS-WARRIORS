## 1. Scope and the Stage 4.8 baseline

**Stage 4.8 already delivered the emergency domain and API** (models,
migrations, C10 access grants, anti-spam throttle, idempotency, lifecycle
respond/escalate/resolve/cancel, admin monitoring, notifications/audit) plus a
basic Flutter emergency page. Stage 4.9 therefore **extends and hardens** that
surface rather than rebuilding it. No duplicate models, services, permission
codes, notifications or API patterns were introduced (per the stage directive).

> **Directive reconciliation.** The 4.9 work item used illustrative vocabulary
> that conflicts with the approved documentation and the shipped 4.8 code. As
> the directive itself instructs ("if the documentation contains a specific
> workflow/field/permission/lifecycle, follow that documentation rather than
> inventing"), the approved SSoT was followed:
>
> | Illustrative value | Approved value used |
> |---|---|
> | `/api/v1/...` | `/api/...` (monorepo convention; no `v1` namespace) |
> | `SICKLE_CELL_CRISIS`, `SEVERE_PAIN`, ... | `MEDICAL PAIN_CRISIS BLOOD FALL OTHER` |

## 3. Security review

- **Deny by default preserved:** queryset scoping unchanged; a foreign patient
  gets 404/403 and an anonymous caller 401 (covered by tests and the gate).
- **No new bypass:** validate requires `emergency_requests.manage`; the owner
  (who holds `view` only) is denied.
- **Auditability:** create/validate/respond/escalate/resolve/cancel/view are all
  recorded; no medical payload is written to security events.
- **PII minimisation:** the owner-facing responder timeline carries role/status
  only, not responder email.
- **Location privacy:** precise coordinates (when supplied) are only returned to
  the requester, active responders and admins by virtue of the existing queryset
  scoping; they are never exposed to unrelated users.
- **Rate limit + idempotency:** unchanged from 4.8 (BR-009); the 503/network
  path cannot masquerade as a successful alert.

## 5. Documented decisions / discrepancies (no silent divergence)

1. **Emergency domain owned by Stage 4.8.** 4.9 extends it; the illustrative
   "rebuild the emergency entities" reading was not followed because the code
   and design already existed.
2. **No "one active emergency per patient" constraint.** The requirements/design
   do not specify one; BR-009 anti-spam is enforced by the per-user throttle
   (3/hour) plus the server-side idempotency key, and the approved 4.8 tests
   create multiple requests. The directive's "only if the design specifies"
   condition was not met.
3. **Rate-limit window discrepancy (pre-existing).** `security-design.md` §12
   lists `5/day, burst 2/10 min` while the shipped throttle is `3/hour`. 4.9
   does not change the throttle; flagging for a design decision.
4. **No GPS dependency added.** Location is captured as approved free-form JSON
   with coordinate validation; automatic GPS capture needs an approved
   dependency + platform permission config and was not invented.
5. **Responder sub-states.** `EN_ROUTE/ARRIVED/DONE/DECLINED` exist as CHECK
   values but have no documented endpoint in the endpoint matrix, so no
   transition API was invented; `respond` creates the `ACKNOWLEDGED` entry.
6. **`patient` FK vs `patient_profile_id` (pre-existing).** The shipped model
   uses a `User` FK per the approved ERD; database-design row 302 names
   `patient_profile_id`. Unchanged in 4.9; flagged for reconciliation.

## 6. Deferred (explicitly out of Stage 4.9)

- Responder state machine beyond acknowledgement + operator console UI.
- Push/FCM delivery of emergency notifications (AD-MD-9).
