## 1. Scope

Deliver the approved **blood donation/matching** and **emergency response**
modules, plus the **notification** and **audit** seams they depend on:

- Blood donor self-profile (FR-BLD-001..004), request submission (FR-BLD-005),
  verification before public visibility (FR-BLD-006 / BR-005), matching
  (FR-BLD-007/008), donor response (FR-BLD-009), donation recording.
- Emergency quick request (FR-EMG-001/002) under per-user rate limiting
  (BR-009), lifecycle (respond/escalate/resolve/cancel), C10 bounded access
  grants, admin monitoring (FR-EMG-005/006).
- Recipient-scoped notification inbox + preferences (FR-NOT-001..006), used by
  the matching and emergency flows via an internal `NotificationService`.
- Facilities directory (verified venue picker) and the audit log surface.

NOT in scope (later stages): push/FCM delivery (AD-MD-9), community module,
payments, full consent graph (C2/C3), analytics.

## 3. Data model (approved rows, quoted)

> `blood_donors`: `user_id` FK, `blood_group` CHECK, `region`, `city`,
> `is_available`, `is_verified`, `donation_count`, `last_donation_date`.
> `blood_requests`: `uid`, `created_by_id`, `patient_id`, `blood_group_needed`
> CHECK, `units`, `urgency` CHECK(NORMAL URGENT CRITICAL), `facility_id`,
> `reason`, `location`, `status` CHECK(PENDING_VERIFICATION ACTIVE MATCHING
> MATCHED FULFILLED EXPIRED CANCELLED REJECTED), `verified_by_id`,
> `verified_at`, `rejection_reason`, `idempotency_key` unique.
> `blood_matches`: `request_id`, `donor_id`, `match_score`, `match_reason`,
> `status` CHECK(SUGGESTED NOTIFIED ACCEPTED DECLINED FULFILLED EXPIRED),
> `notified_at`, `responded_at`, `fulfilled_at`.
> `blood_donation_events`: `donor_id`, `request_id`, `facility_id`, `units`,
> `donated_at`, `outcome` CHECK(COMPLETED DEFERRED FAILED), `donation_serial`,
> `recorded_by_id` (immutable history).
> `emergency_requests`: `uid`, `requester_id`, `patient_id`, `severity`
> CHECK, `type` CHECK(MEDICAL PAIN_CRISIS BLOOD FALL OTHER), `location` JSONB,
> `description`, `status` CHECK(CREATED VALIDATING ACTIVE RESPONDING ESCALATED
> RESOLVED CANCELLED EXPIRED), `rate_limit_ok`, `phone_verified`, `escalated_at`,
> `resolved_at`, `idempotency_key` unique.
> `emergency_responders`: `request_id`, `responder_id`, `responder_role`,
> `status` CHECK(NOTIFIED ACKNOWLEDGED EN_ROUTE ARRIVED DONE DECLINED), timestamps.
> `emergency_access_grants`: `patient_id`, `grantee_id`, `scope`, `reason`,
> `status` CHECK(ACTIVE EXPIRED REVOKED), `starts_at`, `expires_at`.
> `notifications`: `recipient_user_id` FK, `type` CHECK(.. EMERGENCY ..),
> `channel` CHECK(PUSH IN_APP EMAIL SMS), `title`, `body`,
> `related_resource_type/id`, `status` CHECK(PENDING SENT DELIVERED READ FAILED
> SUPPRESSED), `delivery_key` nullable-UNIQUE, `read_at`, `sent_at`, `created_at`.
> `notification_preferences`: `user_id`, `category` CHECK(mirrors type),
> `enabled`, UNIQUE(user_id, category).

Implementation notes:
- Matching vocabulary `RECIPIENT_ACCEPTABLE_DONORS` (recipient → acceptable
  donor groups) is the in-code SSoT. Score = exact `0.300` / compatible `0.200`
  / history `min(count,5)*0.02` / same region `0.050` / same city `0.100` /
  available `0.150`. `run_matching` runs only for `MATCHABLE_STATUSES`
  (`PENDING_VERIFICATION`, `ACTIVE`), is idempotent per (request, donor), and
  notifies donors with `delivery_key=blood:match:{pk}`.
- `notifications.status` includes `READ`; emergency notifications are never
  suppressible (`FORCED_CATEGORIES = {"EMERGENCY"}`).
- `idempotency_key` is surfaced as an explicit serializer field so duplicates
  return **409 IdempotencyConflict**, never a DRF auto-`UniqueValidator` 400.

## 5. Ownership, permission and audit (deny-by-default)

- ViewSets filter by owner / active responder / recipient; foreign uids resolve
  to **404**, never 403-with-payload (IDOR-safe by construction).
- `permission_classes` entries are **classes**; the new `require("code")` factory
  in `accounts/permissions.py` builds them. (Instance-style
  `HasPermission("code")` is not callable in DRF — corrected across all views.)
- Emergency admin monitoring is gated by `IsAdmin` (SUP/ADM) — HOSPITAL holds
  `emergency_requests.manage` but must 403 here (C4).
- Every mutation writes a `SecurityEvent` (event type only, §21/§24) and an
  `AuditLog` row via `record_audit`; `user_agent` defaults to `""` when no
  request context is available (column is NOT NULL).

## 10. Discrepancies / deviations

- **Facilities permission codes** are not enumerated as a dedicated matrix
  section; codes (`facilities.verify`, `facilities.self_manage`) were derived
  from the endpoint-matrix §6 auth columns (SUP/ADM/VO and HOSPITAL). Recorded
  for reviewer confirmation.
- **URL namespace:** the endpoint matrix writes paths under `/api/v1/...`; the
  implemented and tested surface follows the existing repository convention at
  `/api/...` (consistent with 4.1–4.6). A future version-prefix change would be
  applied uniformly.
- `notifications` CHECK constraint was created in `0003` and re-created in
  `0004` to include the `READ` status; migrations remain fresh-apply clean.
