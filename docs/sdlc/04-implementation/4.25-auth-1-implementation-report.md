## 1. Doctor Professional Verification (BR-001, FR-DOC-001..004)

**Model** — `doctors/models.py` `Doctor` (db table `doctors`): `user` OneToOne
(`doctor_profile`), nullable `facility`, `license_number`, `specialty` (code),
`registration_body`, `verification_status`
CHECK(PENDING APPROVED REJECTED SUSPENDED), `verified_by`, `verified_at`,
`verification_expires_at` (null — DBD-5 tracked, not blocking), `rejection_reason`,
`is_active`, timestamps + `doctors_status_created_idx`. Migration
`doctors/0003_doctor.py` (deps: doctors 0002, facilities 0003).

**Identity rule (BR-001):** `User.is_verified_doctor` now requires
active DOCTOR role **AND** `account_status == ACTIVE` **AND**
`doctor_profile.verification_status == APPROVED` (lazy; miss → False).
**Registration never auto-approves** — a DOCTOR account has no `Doctor` row and
is unusable in clinical flows until approved.

**Endpoints (`doctors/urls.py`, under `/api/`):**
- `GET/PATCH /doctors/me/` — own profile (`doctors.self_manage`), row auto-created.
- `POST /doctors/me/verification/` — submit/update; → PENDING; re-submit allowed
  from REJECTED only; writes `accounts.VerificationDocument` rows (PENDING);
  audited `doctors.verification_submit`; `DOCTOR_VERIFICATION_SUBMITTED`.
- `GET /doctors/`, `GET /doctors/{uid}/` — public registry subset (name, specialty,
  registration body, facility), **approved+active only**, no license/contact PII.
- `GET /admin/doctors/verification-queue/` — PENDING applications (`doctors.verify`, C6).
- `POST /admin/doctors/{uid}/verify/` — one unified endpoint (VO/ADM/SUP) decides
  approve **or** reject; rejection requires a reason; every decision audited
  `doctors.verify` + `DOCTOR_VERIFIED`/`DOCTOR_REJECTED`.
- `POST /admin/doctors/{uid}/suspend/` — reason required; audited + `DOCTOR_SUSPENDED`.

**Gating consumers (existing):** patient→doctor chat `ConversationViewSet._partner_error`
(C13b) and `accounts/permissions.py IsVerifiedDoctor` now resolve against the real
registry. The 4.20 integration test that started a chat with a bare DOCTOR user was
updated to create an APPROVED registry row (real-change honesty).

## 2. Caregiver Relationships (§8.1, C14)

**Model** — `patients/models.py` `CaregiverRelationship` (db table `caregivers`):
UNIQUE(patient, user), `relationship_type` CHECK (PARENT/SPOUSE/CHILD/SIBLING/
GUARDIAN/FRIEND/OTHER), `status` CHECK(PENDING ACTIVE REVOKED EXPIRED), `invited_by`,
`accepted_at`, timestamps + `caregivers_user_status_idx`. Migration `patients/0002`.

**Endpoints (`patients/caregivers_urls.py`, router mounted at `/api/`):**
- `GET/POST /api/caregivers/` — patient invites (PENDING); invitee must be an
  ACTIVE CAREGIVER-role user; audited `caregivers.invite` + `CAREGIVER_INVITED`.
- `POST /api/caregivers/{id}/accept|decline/` — invitee only → ACTIVE (accept)
  / REVOKED (decline, see caveat §14); audited.
- `GET/PATCH /api/caregivers/{id}/permissions/` — patient-owned consent scope for
  the link (create/amend the ACTIVE `Consent` for the pair); audited + `CONSENT_GRANTED`.
- `DELETE /api/caregivers/{id}/` — patient-owned; REVOKED + its consents REVOKED
  (FR-MEDREC-005 immediate), audited + `CAREGIVER_REVOKED`.
- `GET /api/caregivers/me/patient/` — **CAREGIVER role alone grants nothing**: read
  requires an ACTIVE link AND `patients.view` in an ACTIVE consent; returns
  PHI-free basics only (name + relationship), no DOB/genotype/diagnosis.

## 3. Consent Authorization (§9, FR-MEDREC-005)

**Model** — `medical_records/models.py` `Consent` (db table `consents`): patient
grantor, grantee (`granted_to`), nullable `authorized_role`, `resource_type`
CHECK(patients medical_records medications symptoms appointments health_timeline
emergency), `resource_ids` JSONB, `permission_scope` JSONB
(`module.resource.action` codes), `purpose`, `start_date`, `expires_at`,
status CHECK(DRAFT ACTIVE REVOKED EXPIRED), `revoked_by`, `revoked_at`, timestamps.
Migration `medical_records/0001`.

**Service** (`medical_records/services.py`): `expire_due()` (lazy ACTIVE→EXPIRED
on DB clock), `active_scope(patient, grantee)` (union of live consent codes),
`can_access(...)`, `grant/revoke/renew`.

**Endpoints (`medical_records/urls.py`, router at `/api/`):**
- `GET/POST /api/consents/` — list (owner/named grantee/C4) and grant (PATIENT).
- `GET /api/consents/{uid}/`, `PATCH /api/consents/{uid}/` — read + owner-gated amend.
- `GET /api/consents/active/` — C2 grantee evaluation (union of ACTIVE scopes).
- `POST /api/consents/{uid}/revoke/` (immediate), `POST .../renew/` — PATIENT/owner
  only; every action audited (`consents.grant/revoke`) + SecurityEvents
  `CONSENT_GRANTED/RENEWED/REVOKED`.
- List scoping: owner, named grantee, or SUP/ADM (C4 oversight).

## 4. Emergency Access Override Auditing (C10, FR-EMG-006)

`emergencies/services.py`: issuance in `create_emergency`/`_ensure_grant` now
records `emergency.access_grant` with `details={"action":"issue", grantee,
patient, reason, expires_at}` + `EMERGENCY_ACCESS_GRANTED`; `resolve` → grants
EXPIRED + audit `action=expire` + `EMERGENCY_ACCESS_REVOKED`; `cancel` → grants
REVOKED + audit `action=revoke`. No new permission code was minted (caveat §17).
