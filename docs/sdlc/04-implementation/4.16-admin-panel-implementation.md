## 1. Scope

Deliver the approved **backend** of the admin panel — the web client is a deferred
client stage (see §7). Four invariants shaped the build:

1. **Failed-open-as-failed-closed.** Every sensitive mutation authorizes
   **before** payload validation (403 precedes any 400) and writes an append-only
   audit row with the operator's `reason` (min 5 chars).
2. **C17 privilege boundaries.** Privileged = `SUPER_ADMIN`, `ADMIN`. A self
   role-change is always denied; ADMIN may only grant/revoke non-privileged roles,
   may not touch a privileged account'status/roles, may not self-deactivate, and
   the last role on an account is never revocable.
3. **Value-surface discipline.** User rows carry identity + RBAC only (zero
   medical/donor/financial fields). No audit read/export exposes free-form
   `details`. AI monitoring returns counters only — never conversation content.
4. **Read-only financial admin.** Totals read **only** from CONFIRMED ledger rows
   (COMPLETED donations / PROCESSED refunds); payment confirmation stays
   provider-webhook-only (BR-008). System settings remain **NOT IMPLEMENTED
   BECAUSE NOT APPROVED** (the AD-A-8 api gap was not cleared to build).

## 4. Security review

- **Authorize-before-validate.** Privilege checks run before reason/body
  validation so a 403 from a failed authorization can never be masked by a 400
  from malformed input. Verified by unit tests + gate.
- **C17 matrix tested.** Self role-change / self-deactivate denied; ADMIN cannot
  grant/revoke privileged roles or touch a privileged account; last-role revoke
  400; unknown user 404 (no IDOR); reasons are audited on every grant/revoke/
  activate/deactivate.
- **MFA boundary.** `MfaPolicy` gates every admin surface + audit export +
  broadcast + financial summary + campaign lifecycle; refusal records
  `MFA_CHALLENGE` and never touches an mfa_enabled **patient's** general surfaces.
- **Payload-free by policy.** User rows are an allow-listed identity+RBAC set;
  audit serializer/CSV carry no `details`; AI monitoring emits counters only
  (test asserts no prompt/content tokens appear in the body).
- **Shorter admin session.** Admin login and every refresh issue an 8h refresh
  token (patients 24h) — verified against the JWT `exp` claim.
- **Confirmed-ledger only.** Financial totals derive from COMPLETED donations /
  PROCESSED refunds; PENDING rows are reported separately and never summed.

## 6. Documented decisions / discrepancies (no silent divergence)

1. **`roles/` is one method-agnostic DRF route**, not three same-path actions —
   DRF's `DefaultRouter` would register three identical regexes and Django would
   resolve them all to the first, 405'ing DELETE/GET. A single `@action(methods=
   ["get","post","delete"])` dispatches by `request.method` (see
   `accounts/admin_views.py`).
2. **Last-role revocation is blocked (400).** An account always keeps ≥1 active
   role (registration grants exactly one); there is no orphan-account path.
3. **Campaign `pause`/`close` and `AdminCampaignAccess` now enforce the MFA
   boundary**, extending 4.12's verify surface — mfa_enabled admins on verify are
   also refused. No test regression: legacy tests use mfa_enabled=False.
4. **Admin session TTL is applied at token issuance/rotation, not on a
   serializer change of `SIMPLES_JWT` settings** — the setting
   `ADMIN_REFRESH_TOKEN_LIFETIME` feeds `token_pair_for` per-user so patients keep
   their 24h while admins get 8h.
5. **`tests_admin.py` modules are per-app** (one per surface) rather than a single
   `admin` mega-module — the repo's test-discovery convention (`test*.py`) and the
   per-app boundary of each surface.
