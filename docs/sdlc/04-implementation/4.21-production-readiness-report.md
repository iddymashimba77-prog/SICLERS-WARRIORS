## 1. Repository & Env Separation

- Clean separation: `development`, `staging`, `production`, `ephemeral_test`,
  `test_settings`, `base`. Production/staging **fail closed** at import (refuse
  placeholder `DJANGO_SECRET_KEY`, refuse missing/placeholder payment secrets,
  require explicit `PAYMENT_ENV`).
- Development module is deliberately relaxed (DEBUG, open CORS/hosts, console email).
- `.env` is gitignored (dev values only); `.env.example` ships placeholders only.
- DB-name separation: dev `sickle_cell` (5432); prod must be a distinct database
  (e.g. `sickle_cell_prod`, 3.9 catalogue) with its own role.
  **Classification: READY**

## 2. Production Settings Audit

- Verified via `check --deploy` on the production module: **0 errors, 0 security
  warnings** — HSTS preload, SSL redirect, secure cookies, fail-closed secrets.
- Conditions at deploy time: `ALLOWED_HOSTS` and `CORS_ALLOWED_ORIGINS` must be
  populated (empty value fails fast with `corsheaders.E013` — desirable), HTTPS
  termination at the proxy, `SECURE_PROXY_SSL_HEADER` behind nginx.
  **Classification: READY WITH CONDITIONS**

## 3. Secrets & Credential Audit

- No keys/credentials in commits; `.env` ignored; only `.env.example` tracked.
- Two dev-only literals noted (both localhost/dev, low risk): dev DB password in
  `scripts/setup_system_pg.sh` and dev values inside dev `.env`. Rule for Stage 5:
  never reuse the dev password; rotate everything at provisioning.
  **Classification: READY (with the dev-credential note above)**

## 4. Dependency Audit

- `requirements.txt` fully pinned and matches the installed venv exactly (Django
  6.1.1, DRF 3.18.1, simplejwt 5.5.1, cors-headers 4.9.0, drf-spectacular 0.30.0,
  psycopg[binary] 3.3.5, python-dotenv 1.2.3, Pillow 12.3.0). Minimal surface; no
  surprise packages.
- Flutter deps minimal (`http`, `cupertino_icons`, `flutter_lints`).
- No automated CVE scanning exists (no CI). Recommend adding `pip-audit`/Dependabot
  as part of the Stage-5 CI work (blocker B1).
  **Classification: READY WITH CONDITIONS**

## 5. Database Readiness

- 78 migrations; `makemigrations --check` clean (models in sync).
- Fresh empty DB migrates end-to-end without error.
- Portable to Postgres? Migrations use standard fields only and psycopg is present,

  are SQLite-ephemeral by policy). Also `DB_SSLMODE` not wired for remote links.
  **Classification: READY WITH CONDITIONS**

## 6. Backup / Restore Plan (RPO/RTO)

- Delivered in `4.21-operations-plan.md` §2: encrypted `pg_dump` daily (RPO ≤24h,

- **No backup exists yet and no drill has run** → RPO/RTO are unproven.
  **Classification: NOT VERIFIED (plan READY)**

## 7. Redis / Worker Readiness

- No Redis installed or required. Background jobs are **DB-backed**
  (`core.jobs.BackgroundJob` + `process_jobs` command) with stale-runner re-claim
  (900s) — runs via cron/systemd, no daemon needed. Optional Redis cache is
  documented (`CACHE_URL`) but LocMem (per-process) is the default; production with
  >1 worker must accept per-process throttling or enable Redis.
  **Classification: READY WITH CONDITIONS**

## 20. Mobile Permissions — Remedy Applied During This Stage

- **Found and fixed release blocker:** the main `AndroidManifest.xml` did not declare
  `INTERNET` (only debug/profile manifests did), so release builds had no network
  permission. Added `android.permission.INTERNET` to `app/src/main/AndroidManifest.xml`.
- No other permissions are requested, which is correct for the current feature set
  (no camera/location/storage needed); no usesCleartextTraffic — production traffic
  must be HTTPS (release default blocks cleartext, expected).
- **Verified in the built release APK** via `aapt2 dump permissions`: only
  `android.permission.INTERNET` (+ Flutter's standard
  `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`).
  **Classification: FIXED — READY (verified on artifact)**

## 35. Release Blockers & Acceptance Criteria

Blockers carried to `4.21-operations-plan.md` §8: **B1** no CI/CD + zero-commit/no
remote; **B2** release signs with debug key (confirmed on the 4.21 APK); **B3**
FCM/email/SMS unimplemented; **B4** admin web not buildable; **B5** no physical
device verification; **B6** Postgres-only validation + no restore drill.

Acceptance for a Stage-5 release (all required):
1. Git history exists on `main` with protected branch + CI green (lint, tests, gate,
   `check --deploy`, CVE scan).
2. Production release APK building with the **release keystore** and correct
   `--dart-define=API_BASE_URL`; a store-ready artifact shown; device smoke passed.
   (Build/packaging already proven this stage — 51.3 MB APK with `INTERNET`
   permission and baked production URL.)
3. Backend deployed per runbook Steps 0–9; `health/ready` green through the proxy.
4. A recent restore drill has succeeded (RPO/RTO evidenced) and pre-release backup taken.
5. Notifications scope frozen (in-app-only or channels implemented) — no implicit
   promises.
6. Admin web either excluded from the release statement or delivered buildable.
7. All secrets provisioned via the secret manager; `.env`-dev values never reused.
8. 4.20 gate reruns green against the deployed environment.

> Overall verdict: **NOT RELEASE-READY** pending B1–B6; the engineering base is
> RELEASE-CANDIDATE at code level with the above conditions met.
